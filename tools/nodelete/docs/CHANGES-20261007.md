## 2026-10-07 11:37:32 — 重写 NoDelete，修复多个实际缺陷

### 新增
- `build.sh`：MinGW-w64 编译脚本，产出图形版 `NoDelete.exe` 与控制台版 `nodelete-cli.exe`
- `install-sendto.ps1`：一键安装/卸载「发送到」菜单三个入口（禁止删除/允许删除/切换保护状态）
- `README.md`：原理、用法、退出码约定、已知限制

### 修复（原实现存在的问题）
1. **路径不存在时误保护上级目录**（严重）
   原 `nd_resolve_dir` 把任何"非目录"都当作文件并取其父目录，
   路径拼错时会静默给上级目录加保护且返回成功。
   现改为：路径不存在直接返回错误码 3，绝不回退父目录。
2. **错误时退出码仍为 0**
   `nodelete_core` 的失败分支提前 return 未写回 `r->status`，
   导致脚本无法判断成败。现所有失败路径统一写回状态。
3. **UNC 路径前缀非法**
   `\\server\share` 直接拼前缀得到 `\\?\\server\share`（非法）。
   现正确转换为 `\\?\UNC\server\share`。
4. **控制台输出乱码**
   宽字符直接输出，重定向到管道/文件得到 UTF-16 字节流。
   现统一转换为 UTF-8 字节输出，控制台/重定向/管道均可读。
5. **目录末尾多余反斜杠**
   路径带尾随 `\` 时会拼出 `dir\\.NO_DELETE.` 畸形路径，现已规范化。
6. **安装脚本中文乱码 / 菜单项命名错误**
   ps1 缺 UTF-8 BOM 被按 GBK 解析；Hashtable 的 `.Name` 取不到键值。
   已加 BOM 并改用 PSCustomObject。

### 可靠性增强
- 创建后立即回读验证标记确实可访问，失败即报错，不假装成功
- 幂等：重复 create/remove 均返回成功
- `status` 子命令（只读查询）
- `--quiet` 静默模式 + 机器可读输出 `状态<TAB>目录`
- 完整退出码约定（0成功/1参数/2权限/3路径/4创建/5删除/6路径处理）
- 静态链接，图形版无控制台窗口闪烁
- 核心逻辑与界面分离，`nodelete_core()` 供两个入口共用

### 验证
以 `SHFileOperationW`（资源管理器实际使用的删除 API）验证：
受保护目录（含子文件递归删除）返回失败码，解除保护后删除成功；
13 项回归测试全部通过；构建零警告。

## 2026-10-07 11:52 — 修复构建脚本（Windows 无 bash / MSYS2 路径不识别）

### 问题
- `build.sh` 在 pwsh 中完全无法使用：Windows 上没有原生 bash，
  用户的实际终端是 pwsh。
- 原 `build.sh` 依赖 MSYS 路径（`/c/...`）与 `-B` 变通写法，
  在 MSYS2 自己的终端里反而多余且脆弱。

### 修改
- **新增 `build.ps1`**（pwsh 版，现为 Windows 上的主入口）：
  自动探测 gcc（参数 → PATH → MSYS2 ucrt64/mingw64/clang64 → W64DevKit），
  并把工具链目录临时前置到 PATH，编译结束后还原，不污染环境。
  支持 `-Clean` / `-Compiler` / `-NoStatic`。
- **`build.sh` 改为面向 MSYS2**：直接使用 PATH 中的 gcc（MSYS2 终端
  启动时已在 PATH 中），仅在找不到时回退到已知安装位置；新增 `--clean`。
  不再使用 `-B` 和 MSYS 路径变通。

### 关键发现（实测）
gcc 依赖 PATH 查找同目录的 `as` / `ld`，否则**静默失败**：
`cannot execute 'as'  CreateProcess: No such file or directory`。
这正是两个脚本都必须把工具链目录加入 PATH 的原因；
手工直接调用 gcc 而不配 PATH 时，会看到"无任何报错但退出码 1"的现象。

### 验证
- `build.ps1`：在 PATH 仅含 system32 的干净环境下，自动找到
  `msys64/ucrt64/bin/gcc.exe` 并成功构建，零警告
- `build.sh`：在 MSYS2 UCRT64 / MINGW64 / MSYS 三种环境下均构建成功
  （前两者用 PATH 中的 gcc，MSYS 自动回退到已知路径）
- 两种脚本产出的二进制均通过 10 项功能回归，
  `SHFileOperationW` 验证保护/解除均正常

## 2026-10-07 11:58 — 调整产物名称 + 修复「发送到」安装权限问题

### 产物重命名（按使用习惯）

|---|---|---|
| `nodelete-cli.exe` | **`nodelete.exe`** | 控制台版 |
| `NoDelete.exe` | **`NoDeleteGUI.exe`** | 图形版 |

同步更新：`build.ps1` / `build.sh` 的产物名与编译顺序、

（构建顺序也调整为先 CLI 后 GUI，与命名顺序一致。）

已验证子系统正确：`nodelete.exe` = Windows CUI（控制台），
`NoDeleteGUI.exe` = Windows GUI（无控制台窗口）。

### 修复：「发送到」菜单装不上（Access denied）
现象：已存在的 `.lnk` 无法删除/覆盖，报 `UnauthorizedAccessException`。

排查结论：**不是脚本缺陷**，而是 UAC 行为——「发送到」目录在
UAC 启用时属受保护位置，**新建文件允许，但删除/覆盖既有文件被拒绝**。
证据：
  - 当前进程非管理员（`IsAdmin: False`），`EnableLUA=1`
  - 新建 + 删除自建文件：成功
  - 原样写回既有 `.lnk`：失败
  - 本工具从未碰过的 `FolderLock.lnk` 同样无法修改
  - ACL 中当前用户已是 FullControl（排除权限问题）
  - 全新 pwsh 进程中依然失败（排除 COM 句柄残留）

改进：脚本现在会**自动检测**该限制并以管理员身份重启自身
（`Test-CanModifyExisting` 探测"能否覆盖既有文件"，
而非新建/删除——后者测不出问题）。仅在确需修改既有快捷方式时才提示。

同时显式 `ReleaseComObject` 释放 WScript.Shell，避免 .lnk 被占用。
实测：自动提权后三个菜单项均成功更新为 `NoDeleteGUI.exe`。

## 2026-10-07 12:10 — 嵌入应用图标与版本信息

### 新增
- `src/nodelete.rc`：资源脚本。含应用图标（`1 ICON "delete.ico"`）
  与 `VS_VERSION_INFO` 版本信息（产品名、版本号、中文描述、语言 0804/1200）。
- `src/delete.ico`：用户提供的图标，内含 16/32/48/64/128/256 六个尺寸，
  全部 32 位带 alpha（PNG 载荷），适合资源管理器/任务栏显示。

### 构建流程改动
`build.ps1` 与 `build.sh` 均新增 windres 步骤：
`windres -i nodelete.rc -O coff -o nodelete_res.o`，
再把 `.o` 与 `nodelete.c` 一起链接进 **NoDeleteGUI.exe**。

图标只给图形版：`nodelete.exe` 是控制台子系统（CUI），图标在终端里
没有显示场景，嵌入只会无谓增大体积（实测 25.6KB vs 52.7KB）。
若 `windres.exe` 缺失，两个脚本都会给出警告并跳过图标，不中断构建。

### 关键点：RC 文件编码
`nodelete.rc` 首行加了 `#pragma code_page(65001)`。
windres 默认按系统 ANSI 代码页（中文环境为 GBK）解析脚本，
没有这行声明时 `VALUE "FileDescription", "NoDelete 目录删除保护"`
会变成乱码。已实测该行生效：Windows 属性面板正确显示
「NoDelete 目录删除保护」，语言为「中文(简体，中国)」。

### 验证
解析 PE 资源目录确认 `NoDeleteGUI.exe` 含 4 类资源：
ICON(6 张)、GROUP_ICON、VERSION、MANIFEST(MinGW 自动附加)。
逐一比对 GROUP_ICON 内 6 项与源 `delete.ico`：
尺寸 16/32/48/64/128/256、bpp=32、字节数 655/1445/2150/2888/6003/12260
**全部一致**。`nodelete.exe` 确认不含图标与版本资源。
功能回归 12 项全部通过（含 GUI 版加保护/解除，
用 CLI 观测状态，因 GUI 子系统无 stdout）。

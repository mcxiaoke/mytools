## 1. 目标与非目标

**目标**：为 Windows 桌面端（Flutter / Tauri / Go / C++ 原生程序）提供**单文件、极小体积、零外部运行时依赖、崩溃可自愈**的独立自动更新器。

| 目标 | 指标 | 守卫 |
| :--- | :--- | :--- |
| 单文件 | 仅 `updater.exe`，无 DLL、无外部配置 | — |
| 体积 | 目标区间 **400–750 KB**（`~500 KB` 是目标值不是结论，以实测为准） | `TESTING.md` §2 体积守卫 |
| 依赖 | **7 个直接依赖** = `windows-sys` + 6 个第三方 | `cargo metadata` 机械守卫 |
| 一致性 | 单次更新内**全量成功或全量回退**，无"半新半旧" | `TRANSACTION.md` |
| 崩溃自愈 | 任意时刻被强杀/终止/掉电（**依赖 NTFS 元数据日志**，不含应用层目录 fsync 承诺）均可确定性收敛。**前提是调用方遵守启动自检硬性契约** | `TRANSACTION.md` §2.3 |
| 契约兼容 | 完全兼容 Go 版 CLI 与 `.updatekeep` 语义 | `CONTRACT.md` §4 |

**非目标**：增量/差分更新、多目标并行、卸载功能、网络下载（由调用方负责）。

### 2.2 首发排除（及重新纳入的触发条件）

| 排除项 | 为什么可以缓 | 什么条件下必须补 |
| :--- | :--- | :--- |
| **Authenticode 纵深校验（N5）** | 包签名仍是完整的安全边界；它只在"包私钥泄露"这一假设下增值 | 拿到代码签名证书、且需要"私钥泄露也换不掉二进制"的保证时。**当前状态：搁置**（无证书，条件不具备） |
| **`--wait-derived`** | 实验开关，默认关闭 | 不计划纳入，除非 CI/脚本明确需要真实退出码 |
| **版本目录 + 入口 stub（方案 B）** | 需改造安装布局 + 数据目录外移，代价由调用方承担。已预留退出通道 | 调用方愿意改安装布局时——届时**整个事务子系统可删除**，代码量预计减半 |

> **已解除延后**（2026-09-14 21:05）：**看门狗（L2）** 与 **`--rollback-previous` 回退引擎**已实施并纳入交付（见 §2.1）。L2 缺失时的兜底契约（`TRANSACTION.md` §2.3，调用方启动自检同步执行 `--recover`）仍然保留——它是 L3 的触发条件，与 L2 是否交付无关。

> **可延后项的判定原则（v4.3 §19）**：延后项的共同特征是**其失效不会导致目录损坏**。
> 反之，`DESIGN.md`/`TRANSACTION.md` 中的任何一项都不可延后——它们直接决定"失败是否可回滚"。

### 2.3 首发必须同时交付的"契约类"东西（不是代码，但缺了承诺就不成立）

1. **调用方文档必须写明**：应用启动时若发现 `<target>/.updater/journal` 存在，**必须同步执行 `updater.exe --recover --target <dir>` 并等待退出码**后再继续自身启动。（`TRANSACTION.md` §2.3）
2. **调用方清理/扫描逻辑必须把 `.updater/` 加入白名单**，否则会破坏事务或丢失回退能力。（`CONTRACT.md` §4）
3. **发布说明必须列明** `CONTRACT.md` §4 中标 ⚠️ 的语义/布局/流程变化。
4. **坏版本兜底路径必须写明**：首选 `--rollback-previous`（本地保留代还原，无需服务端配合），次选"重下旧包 + `--allow-downgrade`"（保留代缺失时）；次选路径的三个前置条件见 `CONTRACT.md` §5.3。

## 3. 止损线

> 源文档的预算是给**终态**设的（"Tier 0 ≤ 2600 行 WARN"），它约束不了首发膨胀。以下是**作用于首发**的止损线。

| 止损线 | 阈值 | 命中时 |
| :--- | :--- | :--- |
| **首发 Tier 0 产品代码行数** | **≤ 1200 行**（不含 `#[cfg(test)]` 之后） | **就地停下重新评估**，不是"继续写" |
| 首发端到端可跑通（含崩溃窗口真实验证） | 必须在 1200 行内达成 | 同上 |
| 直接依赖数 | 7 | CI 硬失败 |
| 并发原语（线程 / 异步 / 事件循环） | 0 | CI 硬失败 |
| Tier 0 中的非 Win32 间接层 | 0 层 | CI 硬失败 |

**含义**：Go 版是约 960 行 / 25 KB 源码；首发 Rust 版多出"事务 + 崩溃恢复 + 签名 + 版本防护"，取 1200 行为上限是刻意收窄的（源文档的 2600 行是给"含看门狗、RM、进度、Authenticode 全量能力"的终态）。**超出即停，不要靠压缩排版或把核心逻辑硬标 Tier 1 来达标。**

> **实测状态（2026-09-15）**：Tier 0 产品代码 **2716 行**，超出 1200 行首发线、也略超 2600 行终态线。这是**已知且已记录**的偏差：实现按 §2.1 "首发包含" 全清单 + 后加的 L2 看门狗与 `--rollback-previous` 落地，未做压缩排版或降级标注。行数在本项目中按 `PLAN.md` §1.4 的口径只触发 **WARN + 架构评审**，**不阻断交付**——正确性由 F 组不变量与 E 组故障注入保证，而非由行数保证。

## 4. 复杂度约束（本项目的最高优先级约束）

> 背景：本项目**一次性投入、长期直接使用**，因此"功能更全"的收益低于"永不出错"的收益。
> **复杂度是可接受的成本，但必须以可验证的方式把它隔离在安全区外。**
> 完整内容（含不变量清单 I1–I10、单一路径复用表、逐项缩回表、规模预算）见 `PLAN.md` §1。

**硬规则（此处仅列最高优先级的四条）**

1. **任何 Tier 2 失败一律降级为 WARNING，绝不允许改变退出码或事务结果。**
2. **每个新增能力必须独立可关闭**（逐项缩回），现场出问题时可退回 Go 版行为。
3. **禁止第二套实现**：版本状态只读 `.updater/state`、回滚只走 `restore_from`、提交判定只看 Journal 的 `STAGE`、锁只走 `lockfile::acquire`。
4. **新增能力合并前必须同时具备**：分层声明 + 不变量对照结论 + 至少一条故障注入测试 + 至少一条"关闭后行为"测试（Tier 2 另加一条"失效不影响 Tier 0/1 判定"测试）。

## 5. 已决策：选定完整基线

> **决策状态：已拍板（2026-09-14），选定「完整基线」**——代码已按本目录实现并落地（Phase 0–6）。
> 极简版 `../../updater/docs/rust-updater-architecture-design-lite.md` 作为备选路线**不再推进**，仅留档。

| | **完整基线**（本目录） | **极简版** `../../updater/docs/rust-updater-architecture-design-lite.md` |
| :--- | :--- | :--- |
| 代码量目标 | 首发 ≤ 1200 行，终态 ≤ 2600 行 | ~600 行 |
| 崩溃中止一致性 | Journal + 三层恢复（强杀/掉电可收敛） | 内存回滚栈（进程内失败可回滚；**进程被强杀则回滚栈随之消失**） |
| 版本与降级防护 | 有 | 无 |
| 签名 | Ed25519 fail-closed | 无 |
| 看门狗 / 保留上一版 / RM 诊断 | 有（L2 看门狗与 `--rollback-previous` 均已落地） | 无 |

**决策要点**：两者的差别**不在工作量，而在"进程被外部强杀"这一场景是否要覆盖**——桌面环境下杀软终止、启动器清进程树、用户 `taskkill` 都不罕见。

**本项目的选择与代价**：选完整基线，即**接受超出 §3 止损线**——首发 Tier 0 实测 2716 行（见 §3 实测状态），并**同时承担** F 组不变量与 E 组故障注入的测试义务。极简版路线的代价是必须**明文接受**"强杀后目录可能停在半新半旧且无自愈入口"，本项目不接受该代价。

## 6. 明确不做的事

> 来源：源文档附录 B。这些是**主动否掉**的方向，不是"还没做"。

| 不做 | 原因 |
| :--- | :--- |
| 常驻服务 / 计划任务（Omaha、Mozilla Maintenance Service 的做法） | 需安装期一次性授权与常驻组件，与"单文件零依赖、无安装器"的定位冲突；且引入用户不可见的后台进程。代价（per-machine 每次一次 UAC）已显式记录 |
| 差分 / 增量更新（Squirrel delta、MSIX 块级 diff、courgette） | 需服务端保存历史版本并生成差分包；本工具本地更新无带宽压力 |
| 通道 / 分阶段发布 / kill switch | 属服务端职责，由调用方实现 |
| 依赖 MSIX / App Installer 让 OS 代劳 | 需改打包格式与分发链路；且 MSIX 自更新路径本身存在多个已知缺陷，等于把问题转移而非解决 |
| 事务型 NTFS（TxF） | 已被微软弃用 |
| 版本目录 + 入口 stub（方案 B） | 与现有安装布局、用户数据位置、Go 版语义不兼容，代价由调用方承担。已预留退出通道（§2.2） |
| 硬链接复用未变文件 | 原地替换场景不适用；硬链接共享会引入"改一处影响另一处"的新风险 |
| Shell COM（`IShellWindows`）降权 | 需 COM feature + 初始化代码，UAC 下行为不稳定，拿不到子进程句柄 / 退出码 |
| JSON Journal | 崩溃路径不应引入解析器依赖；serde 全套约 +100–200 KB |
| 逐文件 `WANT`/`DONE` 双记录 + 逐行 fsync | 每文件 2 次 `FlushFileBuffers`，大包时不可接受；已用"计划一次落盘 + 备份对账"覆盖同等场景 |
| 默认等待派生链并回传退出码 | 会长期占用自身映像句柄，摧毁 `target/updater.exe` 的自更新能力（降为 `--wait-derived` 实验开关） |
| `GetProcessTimes` 比对创建时间 | 调用方无法提供基准，句柄等待已完全覆盖 PID 重用 |
| 依赖 `GetCommandLineW` 原样直传 | 与"路径绝对化""日志共享"不可兼得；转义正确性可用测试保证，路径正确性不能 |
| 物理路径校验的"全严格"作为默认 | 解析失败不构成越界证据；默认分级，`--strict-path-check` 供高安全场景 |
| 强制关闭占用进程（`RmForceShutdown`） | 会强杀用户程序，与本工具"绝不伤害用户工作状态"的立场冲突 |
| `--splash` 进度窗口（v4.3 删除） | 需 PNG 解码器（依赖预算不允许新增 crate）与窗口消息循环（与"并发原语 0 个"冲突），价值与 `--progress-file` 高度重叠 |
| `--rm-shutdown` 清场（v4.3 删除） | 会静默关闭用户正在使用的程序，与"绝不伤害用户工作状态"的立场冲突；RM 的只读诊断已覆盖排障需求且零风险 |
| 卸载 / 应用清理 | 由应用与系统卸载器负责（沿用既有约定） |

## 2026-09-16 13:38 — 补构建身份（`--version` 与日志首行带 git 哈希 + 构建时间）；`packer` 增 `-V/--build-info`；文档路径改指 `target\dist\`

### 0. 一句话

**同一个 `1.0.0` 会有无数次不同构建，此前无从区分**——`--version` 只有版本号，日志首行也只有版本号，
而本项目 release 构建**不可复现**（同日实测：内容与 feature 都不变、强制重编，sha256 仍不同）。
现在 `build.rs` 注入 git 短哈希（脏则 `-dirty`）+ 构建时间 + target/profile/features，
`--version`（追加，前缀不变）与**日志首行**都能自证身份。顺带把**给使用方看的路径**统一到 `target\dist\`。

### 1. 构建身份（`build.rs` + `src/buildinfo.rs`）

| 字段 | 来源 | 说明 |
| :--- | :--- | :--- |
| `build=` | `git rev-parse --short HEAD`（+ `-dirty`） | 脏判定只看**已跟踪文件**（未跟踪临时文件不影响构建内容） |
| `built=` | 构建时间，UTC ISO 8601（如 `2026-09-16T05:35:36Z`） | 设置 `SOURCE_DATE_EPOCH` 时以它为准（可复现构建约定） |
| `target=` / `profile=` / `features=` | cargo 提供 | 行为相关的开关（如 `restart-manager`）在身份里能看出来 |

呈现位置：`updater.exe --version`（**追加**在既有前缀之后）、**日志首行**
（`updater-rs 1.0.0 starting (mode=…, pid=…, build=7dedc67 2026-09-16T05:35:36Z)`）、
`packer -V/--build-info`、`packer` 的打包摘要行。

**两条设计约束**：

1. **`build.rs` 永不失败**：没有 git / 没有仓库 / 时间异常都写 `unknown`，绝不阻断构建；
   零依赖（只用 `std::process::Command`），不进 `src/` 因而不参与分层扫描。
2. **时间格式化放在 lib 里**（`buildinfo::iso8601_utc`），**不放 build.rs**：构建脚本里的
   `#[cfg(test)]` 永远不会执行，放那里等于没有测试。现在它有已知纪元点
   （1970-01-01 / 2023-11-14T22:13:20Z / 当日最后一秒）与闰年边界（2000-02-29、2004-02-29）的单测。

### 2. `packer` 的"打印自身版本"撞车（单测抓出来的设计错误）

初版照搬 `updater.exe` 的拼写，给 `packer` 也加了 `--version` ——**与必填的包版本参数
`--version <VER>` 直接撞车**（对齐旧脚本的 `-Version`）。单测立刻报出
`expected Run, got Version`：那会让打包命令**静默退化成一个只打印版本的空操作**。
改为 **`-V` / `--build-info`**，并补两条回归守卫：

- `--version 9.9.9` 必须仍被解析为**包版本**；缺它时仍报 `missing required --version`；
- 集成测试断言 `--stage nope --version 1.0.0 --out o.zip` 会走到真正的打包流程（失败于 stage 不存在），
  **而不是**打印身份后退出 0。

### 3. 文档：使用方看到的路径统一到 `target\dist\`

`README.md` 与 `USAGE.md` 里给使用方的命令改为 `target\dist\packer.exe`（此前写的是
`cargo run --features pack --bin packer -- …`），并在 USAGE 开头加了"你会用到的两个二进制"表
（`target\dist\updater.exe` 随应用进安装目录 / `target\dist\packer.exe` 留在发布机）。
顺带修掉 README 顶部两处过期状态（测试 80 → 114 项、体积 422 → 468.5 KB）。

### 4. 契约影响（必须告知调用方）

- **`--version` 是追加式变更**：既有前缀**逐字节不变**，其后追加 `key=value`。
  解析方按"**前缀 + 可选追加**"处理（`CONTRACT.md` §2.1 已写明格式与解析要求，§4 差异表已登记）。

- **`updater.manifest` 未被触碰**：packer 的身份只打 stdout（进 CI 日志），不写清单——
  清单格式是契约物。

## 2026-09-16 12:58 — 落地 `packer`（开发期打包工具）：crate 拆 lib + 二 bin、feature gate、与旧脚本的等价性守卫；顺带发现旧流水线的真实缺陷

### 0. 一句话

按 D1–D4 的决策把打包能力做成了**同 crate 的第二 bin**（`--features pack`，不进发布产物、零 Win32 依赖）：
它复用更新器自己的清单格式、zip 合法性判定与哈希实现，因此**没有第二套实现**；
旧的两个 `.ps1` 按 D2 **暂不删除**，其等价性由**机械守卫**守住（而不是靠人记得同步改两处）。
实施过程中发现旧流水线一个真实缺陷：**stage 里只要放了 `.bootclosure`，旧流程就打不出包**。

### 1. 决策（D1–D4）

| # | 决策 | 落地 |
| :-: | :--- | :--- |
| D1 | 形态 = **(b) 同 crate 第二 bin + feature gate** | `src/bin/packer.rs` + `src/packer/*`（Tier 1）；主产物 0 KB 增量 |
| D2 | 脚本**暂不删**（等真实项目验证后再删） | 两个 `.ps1` 原样保留；等价性由 `tests/packer.rs` 守住 |
| D3 | 代码**可移植**，当前只保证 Windows 可用；macOS 不做 | packer 零 `win32::` 依赖；`is_hidden` 用 `cfg(windows)` 门控 |
| D4 | **一次性做完整**（实施可分阶段） | 5 个阶段全部完成（结构 / 实现 / CLI / 守卫 / 文档） |

### 2. 结构改动：crate 拆成 lib + 两个 bin

`src/lib.rs`（T0，45 行）承载全部模块声明，`src/main.rs` 只剩入口与编排。
**唯一动机**是让第二个 bin 复用同一份实现——这正是 `SCOPE.md` §4.3 的要求。

副作用与处理：

- `windows_subsystem = "windows"` 只留在 `updater` 的 bin（`packer` 是控制台程序，要在终端输出）；
- 拆分后这些模块成了 lib 的 `pub` 项，clippy 开始按"公开 API"口径报 5 条
  （`result_unit_err` + `not_unsafe_ptr_arg_deref` 4 条）。**处理方式是不改可信内核的签名**，
  而在 lib 根加两条附理由的 `allow`：本 crate 是**应用内部 lib**（不发布、无第三方消费者），
  `pub` 只是"给两个 bin 看得见"；为迎合只对"对外 API"有意义的 lint 去改 `transaction::rollback`
  的错误类型或把 `win32::process` 全标 `unsafe fn`，只会把 unsafe 染到调用点并增加无信息的间接。
- 产物体积 +2 KB（477696 → 479744 B），Tier 0 产品代码 +31 行（2879 → 2910，仍是既有的"超 2600 WARN"档）。

### 3. `packer` 实现（Tier 1，约 700 行产品代码）

`walk`（遍历与排除）/ `manifest`（清单生成）/ `closure`（闭包判定 + 排序 + 尾部断言）/ `zip_write`（流式写 zip）
/ `mod`（编排 + 参数解析 + 回读自检 + 摘要）。

**关键判断**（细节见 `docs/PROPOSAL-pack-subcommand.md` §9.2）：

| # | 判断 | 收益 |
| :-: | :--- | :--- |
| 1 | 自检**复用 `pkg::zip_read::scan`**（泛型、不碰 Win32） | 用更新器接受包的那套规则验自己的产物：压缩方法约束、加密拒绝、Zip Slip、**大小写不敏感重复条目**——比旧脚本的自检更强，且没有第二套实现 |
| 2 | 清单列**全部**目录；zip 只写**空**目录 | 与旧脚本语义一致（`DIR:` 行是计划期建目录依据） |
| 3 | 排序用**字节序** | 跨平台确定；旧脚本的 `Sort-Object` 是区域敏感的 ⇒ 判等口径改为"集合 + 清单内容一致"，不要求字节相同 |
| 4 | 隐藏文件照常打包并 `[WARN]` | PowerShell 默认跳过隐藏项是它的无意行为，不是契约；**静默丢文件**比多打几个危险 |
| 5 | 写 zip 与哈希都**流式** | 整包可达 GB 级；与 P1-1 的流式自检同一原则 |
| 6 | `--sign` **显式报错** | 不让 CI 以为包已签名 |

### 4. 副产物：旧流水线的一个真实缺陷（`.bootclosure`）

`gen_manifest.ps1` 的排除表**漏了 `.bootclosure`**（只排 `updater.manifest` 与 `.updater\*`），
把打包配置写进清单；而 `release_pack.ps1` 明确不把它打进包 ⇒ 旧脚本**自己的产物自检**
报"清单声明了 .bootclosure，但包内不存在"并**拒绝出包**。

即：**stage 里有 `.bootclosure` 时，旧流水线打不出包**——而 `.bootclosure` 正是启动闭包规则唯一的覆盖入口。
本次**按 D2 不修改脚本**，改为：packer 两边都排除（不受影响）+ 三处文档记录
（`USAGE.md` §2.1 排障提示、`TESTING.md` §4、本节）+ 等价性用例的夹具不含 `.bootclosure`（注释写明原因）。

### 5.1 构建入口：一次产出两个产物（`scripts/build.ps1`）

`cargo build --release --features pack` **一条命令**即产出两个 bin；`scripts/build.ps1` 只是把输出
收集到 `target\dist\` 并打印大小与 sha256（内部同样只有这一条 cargo 命令）。`verify.ps1` 改为复用它。

**两条实测（第二条推翻了本节初版的"分两次构建"做法）**：

| # | 实测 | 结论 |
| :-: | :--- | :--- |
| 1 | 带 `--features pack` 构建的 `updater.exe` 与默认 feature **大小完全相同**（479744 B） | §3.2 的 "+54 KB"（写侧）是 `packer.exe` 自己的体积——写侧只被它引用，未被引用的代码由 LTO 丢弃。**不构成对更新器的税** |
| 2 | 本项目 release 构建**不可复现**：内容与 feature 都不变、强制重编，sha256 仍不同（大小恒定 479744） | "字节相同"不能作为判据；"先构 packer、再用默认 feature 构一遍 updater"是**无效仪式**，已删除 |

**兜住"写侧不得进入 updater.exe"的是形态守卫**（`check_size.ps1` 断言产物内无 packer 独有字面量），
不是构建顺序——这也正是那条守卫存在的意义。

### 1. 逐条复核结论

| # | 反馈 | 结论 | 处置 |

### 2. ① 超时排障提示

问题真实且症状误导性强：宿主**同步等待** updater 的退出码 → 宿主自己不退出 → 目标进程永不退出
（文件锁也一直被它持有）→ Worker 等满 `--timeout`（默认 60 秒）后中止、退出 2。
集成方看到的只有"更新没发生"，而日志里只有一行 `timeout waiting for target process`，
**不解释为什么、也不说改什么**。

新增 `main.rs::hint_wait_timeout(pid, timeout_secs)`，在**两处**超时点调用
（`update_flow` 的等待 PID、`recover_mode` 的等待 PID），紧跟原有的 `[ERROR] timeout` 行输出一条 `[WARN] hint:`，
明确写出"派生的 0 只表示已交接"与"宿主必须立刻退出、绝不等退出码"。

### 3. ② 的残留缺口：参数错误同样不可见（本次新发现）

原 P1-5 只覆盖了"只输出模式"（`--help` / `--version` / `--dry-run`）。复核时用
**"真实控制台 + 子进程无继承 std 句柄"**（`close_fds=True`，等价于 cmd/PowerShell 直启 GUI 子系统的形态）
逐一探测，发现：

- ✅ `--help` / `--version` / `--dry-run` 计划清单 → 落在控制台上（**这同时关闭了
  `RELEASE-READINESS` P1-5 里"`CONOUT$` 兜底分支未能在本机验证"这条待办**）；
- ❌ `error: unknown arguments: …` / `error: missing required --target` → **一个字符都没有**：
  它们走 `main` 的 `eprintln!` 分支，发生在日志初始化之前，既没有日志文件、也没有可见控制台；
- ❌ `--dry-run` 被拒（precheck 失败）→ 同样只有日志、控制台空白，而 `--dry-run` 恰恰是排障入口。

修法：新增 `win32::console::stderr_usable()` + `main.rs::emit_error()`（与既有 `emit` 对称）；
参数错误与 `--dry-run` 被拒原因统一走它。**stderr 可用时保持 `eprintln!` 原语义**，
因此 `2>文件`、管道抓取、CI 的行为完全不变；只有"确实没人能看见"时才回落到父控制台。

### 4. ③ 进度窗标题派生

`strings.rs` 新增 `gui_title(explicit, launch)`：`--gui-title`（非空白）优先，
否则 `format!("{} - {}", <入口名去扩展名>, updating_short)`，两边都缺时退回原 `default_title`。

- **取入口文件名而不是目录名**：目录名常带版本号（`JigsawFox-1.2.3`）或空格（`Program Files`）。
- 新增字段 `UiStrings::updating_short`（`正在更新...` / `Updating...`）：
  `<AppName> - 正在更新应用...` 里的"应用"是重述，读起来像机器拼接的。
- **绝不产出残缺标题**：无 `--launch`（如 `--recover` 不拉起）时退回纯默认标题，不会出现 ` - 正在更新...`。

- 新增 `--gui-title` 支持空白视为未指定（原来会得到一个全空白标题）。

## 2026-09-16 10:35 — 恢复承诺收缩为 L1+L2；补自身修复入口与打包顺序规则；`--lite` 档位撤销

### 0. 一句话

原来承诺的"**任意时刻被强杀/终止/掉电均可确定性收敛**"是**过强承诺**——
它把"能收敛"当成"能被触发"。本次把承诺范围明确收缩为 **L1 + L2**，
并用两条**不依赖宿主**的路径补上剩下的部分：`updater.exe` 无参数自愈、保留更新包兜底。
同时把"启动闭包排在 zip 末尾"变成打包器的机械守卫。

### 1. 起因：L3 承诺不成立

L3 的触发条件是"下次有 `updater.exe` 被启动"，而这由调用方决定。更关键的一步：

> 一次被中断的更新可能让**启动闭包**停在半新半旧。Windows 的 loader 在**任何用户代码之前**
> 加载入口 exe 的 import 表，因此应用**在 `main()` 之前就失败**——
> 调用方的启动自检代码根本执行不到。

于是"调用方遵守启动自检硬性契约"是**必要而非充分**条件。

### 2. 实测：风险不是角落情况

用**真实 Flutter 产物**（`jigsawpuzzle`，94 文件）按当时打包器的规则（`Sort-Object FullName`，全路径字母序）
复现条目顺序，结果如下：

| 位置 | 条目 | 是否启动闭包 |
| :-: | :--- | :-: |
| 1–2 | `audioplayers_windows_plugin.dll`、`dartjni.dll` | ✅ |
| **3** | **`data/app.so`（Dart AOT 快照，10.4 MB）** | ✅ |
| 4–87 | `data/flutter_assets/*`（84 项资源，惰性加载） | ❌ |
| **88–94** | `icudtl.dat`、插件 DLL、**`flutter_windows.dll`（20.3 MB 引擎）**、**`JigsawFox.exe`（入口）**、其余根级文件 | ✅ |

**启动闭包的 10 个成员分散在第 1、2、3、88、89、90、91、92、93、94 位——跨度 1–94，等于整个事务。**
快照与引擎之间有严格的版本哈希绑定，不匹配则 VM 拒绝加载；因此
**从第 3 项写完之后开始，几乎每一个中断点都可能落在"应用起不来"的组合上**（92/94）。

> 问题纯粹是**文件之间**的版本不一致。

#### ③ 自身修复入口的实现要点

- **判定基于语义而非 token 数量**：`无 --target` 且 `无 --zip/--launch` 且未选其它模式
  ⇒ 视为自身修复。这样 `--silent` / `--debug-console` 这类纯修饰参数能与它同时出现；
  而 `updater.exe --zip x.zip`（写错的更新调用）**仍报 `missing required --target` 并退出 2**，
  **不会**被静默改判为"修 updater 自己所在目录然后返回 0"。
- **Journal 目标必须匹配**：不匹配时拒绝（退出 3）并保留现场，避免放错位置的 updater 去动别人的目录。
- **失败时弹人可见提示框**（release 是 GUI 子系统，双击时没有任何控制台输出）。

#### ④ 打包顺序规则

- 闭包定义：**根目录直系文件** + `data/*.so` / `data/*.dat`；可由打包目录根的 `.bootclosure` 覆盖。
- 顺序：非闭包条目（字母序）→ 空目录条目 → **闭包条目连续收尾**。

  "闭包成员 vs 实际尾部"。
- **变异测试已验证守卫非空转**：把顺序改回纯字母序 → 打包立即失败（退出 1），
  错误信息列出 10 个闭包成员与实际尾部 10 项的差异，并给出修复方向。
- 在真实产物上实测：**95 条目，闭包 10 个连续位于末尾**，风险跨度 94/94 → **10/95**。

### 4. 一个自引入的缺陷（记录在案）

③ 的提示框**首版没有"有没有人在看"这个门条件**，导致：

- 模态框会**阻塞主线程**（本项目并发原语为 0，不能开工作线程弹框）；
- 测试用例以管道捕获 stdio 拉起 updater，失败路径命中弹框 ⇒ **`self_repair` 测试套被挂住 20 多秒**，
  直到人工点掉才结束（套件耗时从 4.6s 变成 27.9s）。

## 2026-09-16 10:35 — 恢复承诺收缩为 L1+L2；补自身修复入口与打包顺序规则；`--lite` 档位撤销

### 0. 一句话

原来承诺的"**任意时刻被强杀/终止/掉电均可确定性收敛**"是**过强承诺**——
它把"能收敛"当成"能被触发"。本次把承诺范围明确收缩为 **L1 + L2**，
并用两条**不依赖宿主**的路径补上剩下的部分：`updater.exe` 无参数自愈、保留更新包兜底。
同时把"启动闭包排在 zip 末尾"变成打包器的机械守卫。

### 1. 起因：L3 承诺不成立

L3 的触发条件是"下次有 `updater.exe` 被启动"，而这由调用方决定。更关键的一步：

> 一次被中断的更新可能让**启动闭包**停在半新半旧。Windows 的 loader 在**任何用户代码之前**
> 加载入口 exe 的 import 表，因此应用**在 `main()` 之前就失败**——
> 调用方的启动自检代码根本执行不到。

于是"调用方遵守启动自检硬性契约"是**必要而非充分**条件。

### 2. 实测：风险不是角落情况

用**真实 Flutter 产物**（`jigsawpuzzle`，94 文件）按当时打包器的规则（`Sort-Object FullName`，全路径字母序）
复现条目顺序，结果如下：

| 位置 | 条目 | 是否启动闭包 |
| :-: | :--- | :-: |
| 1–2 | `audioplayers_windows_plugin.dll`、`dartjni.dll` | ✅ |
| **3** | **`data/app.so`（Dart AOT 快照，10.4 MB）** | ✅ |
| 4–87 | `data/flutter_assets/*`（84 项资源，惰性加载） | ❌ |
| **88–94** | `icudtl.dat`、插件 DLL、**`flutter_windows.dll`（20.3 MB 引擎）**、**`JigsawFox.exe`（入口）**、其余根级文件 | ✅ |

**启动闭包的 10 个成员分散在第 1、2、3、88、89、90、91、92、93、94 位——跨度 1–94，等于整个事务。**
快照与引擎之间有严格的版本哈希绑定，不匹配则 VM 拒绝加载；因此
**从第 3 项写完之后开始，几乎每一个中断点都可能落在"应用起不来"的组合上**（92/94）。

> 补充一个核对中确认的好消息：`ReplaceFileW` 是**单文件原子**的，不会出现"半个 DLL"。
> 问题纯粹是**文件之间**的版本不一致。

### 3. 本次改动的五件事

| # | 动作 | 落点 |
| :-: | :--- | :--- |
| ① | **承诺收缩为 L1+L2**；L3 明确标为"尽力而为" | `SCOPE.md` §1、`USAGE.md` §8.3、`TRANSACTION.md` §2.3、`README.md` |
| ② | **`--recover` 从硬性契约降为可选运维工具** | `TRANSACTION.md` §2.3、`USAGE.md` §2.2/§3、`SCOPE.md` §2.3 |

#### ③ 自身修复入口的实现要点

- **判定基于语义而非 token 数量**：`无 --target` 且 `无 --zip/--launch` 且未选其它模式
  ⇒ 视为自身修复。这样 `--silent` / `--debug-console` 这类纯修饰参数能与它同时出现；
  而 `updater.exe --zip x.zip`（写错的更新调用）**仍报 `missing required --target` 并退出 2**，
  **不会**被静默改判为"修 updater 自己所在目录然后返回 0"。
- **Journal 目标必须匹配**：不匹配时拒绝（退出 3）并保留现场，避免放错位置的 updater 去动别人的目录。
- **失败时弹人可见提示框**（release 是 GUI 子系统，双击时没有任何控制台输出）。
- 新增 `tests/self_repair.rs`：**8 条断言**，含"反误判"与"显式 `--target` 优先"两条边界。

#### ④ 打包顺序规则

- 闭包定义：**根目录直系文件** + `data/*.so` / `data/*.dat`；可由打包目录根的 `.bootclosure` 覆盖。
- 顺序：非闭包条目（字母序）→ 空目录条目 → **闭包条目连续收尾**。
- **机械守卫**：打包后回读 zip 真实条目顺序，断言闭包构成连续结尾；不满足即失败并列出
  "闭包成员 vs 实际尾部"。
- **变异测试已验证守卫非空转**：把顺序改回纯字母序 → 打包立即失败（退出 1），
  错误信息列出 10 个闭包成员与实际尾部 10 项的差异，并给出修复方向。
- 在真实产物上实测：**95 条目，闭包 10 个连续位于末尾**，风险跨度 94/94 → **10/95**。

### 4. 一个自引入的缺陷（记录在案）

③ 的提示框**首版没有"有没有人在看"这个门条件**，导致：

- 模态框会**阻塞主线程**（本项目并发原语为 0，不能开工作线程弹框）；
- 测试用例以管道捕获 stdio 拉起 updater，失败路径命中弹框 ⇒ **`self_repair` 测试套被挂住 20 多秒**，
  直到人工点掉才结束（套件耗时从 4.6s 变成 27.9s）。

**修复**：门条件收窄为**同时**满足 ① 目标由自身目录推断；② 无可用控制台；③ 未 `--silent` / 未 `--debug-console`。
并给 `--silent` 一个**实际作用**（抑制提示框），让无人值守调用有明确的不阻塞开关。

**同时补了防挂死设施**：`tests/self_repair.rs` 的运行器带 **30s 硬超时 + 强杀**，
超时即**断言失败**而不是让测试进程一起卡死——把"挂起"变成"一眼能看懂原因的失败"。

### 5. `--lite` 档位的实现与撤销

为"吸收 lite 行为、以便删除兄弟项目 `updater/`"，本次**先实现了 `--lite` 档位**（P1+P2），
**随后决定撤销**。两段都记录在此，因为撤销的理由比实现本身更有价值。

**实现过什么**（完整留档在 `docs/archive/lite-profile-20260916-superseded/`，带只读说明）：
`src/profile.rs`（档位定义 + 冲突矩阵）、`tests/lite_profile.rs`（6 条断言）、
`JournalWriter.file: File → Option<File>`（全项目唯一持久化开关点）、`main.rs` 4 处短路。
合计 **780 行代码 + 114 行文档**，且 `transaction.rs` / `restore.rs` / `planner::build` / `keep.rs` **零改动**
（满足了 `SCOPE.md` §4.3「禁止第二套实现」）。

**为什么撤销**：

| `--lite` 提供的 | 在"承诺收缩 + 保留 L2"之后的价值 |
| :--- | :--- |
| 免去"启动时同步 `--recover`" | ❌ **归零**——取消 L3 承诺后 full 档也没有这条义务了 |
| 免去 `.updater\` 加白名单 | ⚠️ 仍有效，替代成本是调用方加**一行** |
| 无运行期目录硬门槛 | ⚠️ 仍有效，替代成本是一次性环境核查 |
| 无 `%LOCALAPPDATA%` 自复制 | ⚠️ 仍有效（EDR 未验证），但火绒 6.0.11.3 已实测 9/9 PASS |
| **代价：没有 L2** | 🔴 **恰好砍掉我们刚决定要保留的东西**（L2 覆盖杀软清理 / `taskkill` 等常见情况） |
| 代价：无版本防护 / 无 `previous/` / 无 `--rollback-previous` | 🔴 纯能力损失 |

**净结论**：`--lite` 是用"刚认定有价值的 L2 + 版本防护 + 离线回退"换"三个都有更便宜替代方案的小收益"。
而它存在的初衷是"避免维护两套"——**保留它本身就是把两套从两个仓库挪进一个二进制**，成本降低但没有消除
（永久税：每加一个能力都要回答"lite 档下会怎样"）。撤销后，`SCOPE.md` §5 的"完整基线"决策不再有例外。

## 一、总体评价：应保留的设计资产

1. **密钥分层正确且自包含**：PIN+configSalt → PBKDF2-HMAC-SHA256(600k) → KEK 包裹 MK；MK+fileSalt → HMAC 派生 fileKey；emkBlob 内嵌每个文件，跨机可解。600k 迭代与 OWASP 对 PBKDF2-HMAC-SHA256 的建议值一致，这点优于大量同类小工具。
2. **双模式定位清晰**：结构加密"耗时与文件大小无关"是真实差异化卖点（400MB 亚秒级），整体加密提供密码学级保护；"找不到结构就报错、绝不静默降级"是正确的安全默认。
3. **失败安全已成形**：结构加密内存副本回滚 + footer 提交点判定、还原两阶段、`UniquePath` 绝不覆盖、明文临时文件 finally 清理，均已落地。
4. **工程纪律好**：零第三方加密依赖、HKCU-only 注册表、无遥测、便携模式、空状态引导、关键按钮已埋 `AutomationProperties.AutomationId`（GUI 自动化的现成钩子）、60 项测试全绿。

以下建议按"先修缺陷、再演进架构、后扩展体验"排序。

## 二、新发现的功能缺陷（建议立即修复）

### 2.1 【P0·回归】右键菜单"整体解密/结构解密"对整体加密文件必然失败

- **位置**：`src/HideFiles.App/App.xaml.cs:63-66`；`MainViewModel.cs:481`；`FileObfuscator.cs:254-258`。
- **现象**：启动参数 `--unhide` 与 `--decrypt` 都被硬编码为 `AutoProcessPathsAsync(paths, ProtectionMode.StructureLock, isObfuscate: false)`，注释却写"由容器自动识别模式"。2026-11-18 13:02 引入的 `expectedMode` 严格隔离生效后，右键"整体解密"一个整体加密文件会直接报"该文件不是结构加密文件……请在整体加密工作台解密"；且文件被加入**结构加密**工作台列表（`AutoProcessPathsAsync` 按 mode 选集合），与用户预期完全相反。
- **复现**：整体加密任一文件 → 资源管理器右键 → HideFiles → 整体解密 → 失败。CLI `decrypt` 不受影响（未传 expectedMode），GUI 工作台按钮不受影响（传各自模式），**只有 shell 动词路径回归**。
- **修复建议**：shell 驱动的还原传 `expectedMode: null`（自动识别），并按 `Inspect` 结果把文件路由到对应工作台集合；严格隔离只保留给工作台内的显式按钮。补一条回归测试覆盖"右键动词 × 两种容器"矩阵。

### 2.2 【P1】`ActiveMode` 从未被赋值，Tab 切换与拖拽/投递路由脱节

- **位置**：`MainViewModel.cs:62-64`（注释声称"由 Tab 切换设置"）、`:112`（`CollectionFor(mode ?? ActiveMode)`）。全仓库无任何赋值点；`MainWindow.xaml:37` 只绑定 `SelectedTabIndex`。
- **后果**：`ActiveMode` 恒为 `"struct"`。右键"打开 HideFiles"携带文件（`App.xaml.cs:70` 的 `vm.AddPaths(paths)`）时，即使用户停在"整体加密"页，文件也进结构加密列表。拖拽因按 sender 网格路由而幸免，但语义不一致。
- **修复**：在 `SelectedTabIndex` 的 partial 变更钩子中同步 `ActiveMode`（0/1→struct/secure，设置/关于页保持上一个工作台），或让 `AddPaths` 默认取当前 Tab 对应集合；补 UI 级断言。


### 2.4 【P1】`PinHash` 单轮 SHA-256 仍在，离线爆破绕过 PBKDF2；验证链路只验哈希不验密钥

- **位置**：`HideFilesConfig.cs:44,157-158,190-195`；`PasswordDialog.xaml.cs:149,174`。
- **问题**：config.json 泄露后，`SHA256(PIN+固定盐)` 可被 GPU 高速穷举，600k PBKDF2 的成本设计被完全绕过（11-17 报告 P2-15① 指出后仍未修）。`VerifyPin` 在未设置 PIN 时恒 true（危险默认值）、比较非固定时间；密码对话框只比对哈希，不尝试解 `WrappedMasterKey`，哈希与密钥材料不一致时用户会"验证通过但解密永远失败"。
- **修复**：**删除 PinHash 字段**，统一以"能否解开 emkBlob"作为唯一验证（GCM tag 天然常时、天然防离线快筛）；迁移期读旧配置时兼容但不再写回。对话框 Verify/Change 模式改走 unwrap 验证。

### 2.5 【P1·文档承诺过宽】改密码后，历史文件在**其他机器**上仍需旧密码

- **位置**：`V2Crypto.ResolveMasterKey`（`V2Crypto.cs:152-171`）第三路兜底依赖**本机 config**；README"此前加密的文件仍可用新密码解密"只在本机或持恢复码时成立。
- **后果**：用户改密码后把旧文件拷给同事/换机，对方用新密码必失败，且错误信息不解释原因。
- **修复（高价值新功能 `rekey`）**：容器格式中 `configSalt` 与 `emkBlob` 都是**定长字段**（前置头 offset 12/56；尾部 footer 起始+4/+48，见 `V2Container.cs:131-134`、`V2Tail.cs:23-30`），因此"用新 PIN 重封装历史文件"可以**原地写 76 字节**完成，不触碰主体、与文件大小无关：
  - CLI：`hidefiles rekey <路径...> --current <旧> --new <新>`（或会话已解锁时免旧密码）；
  - GUI：设置页"同步历史文件到新密码"按钮，批量 O(1)/文件；
  - 元数据用 fileKey（MK 派生）加密，与 configSalt 无关，故重封装不影响内容解密；恢复码保持不变。
  - 同时修正 README/关于页措辞，说明"跨机需 rekey 或恢复码"。

### 2.6 【P1·性能】加解密批处理每文件重复跑 PBKDF2，"极速"卖点在批量场景被吃掉

- **位置**：加密侧 `FileObfuscator.cs:138`（每文件 `UnwrapMasterKeyWithPin`）+ `V2Tail.cs:133` / `V2Container.cs:66`（每文件再 `DeriveKek`）≈ 2×100ms/文件；还原侧 `ResolveMasterKey` 优先用 pin 派生（`V2Crypto.cs:158-161`），即使 `_sessionMasterKey` 已缓存也先跑一次 KDF。
- **量级**：1000 个小文件批量加密 ≈ 200s 纯 KDF；架构文档"批量还原只跑一次 PBKDF2"的承诺与实现不符。
- **修复**：① 会话级缓存 MK 与 KEK（configSalt 会话内不变）；emkBlob 仍每文件用**新 nonce** 重封装（32 字节 GCM，微秒级，避免 nonce 复用争议）；② `ResolveMasterKey` 顺序调整为 恢复码 → 本机 fallbackMK（若提供）→ pin 派生，本机文件零 KDF、外来文件才付费；③ 引擎 API 显式接收密钥材料（见 3.1），CLI/GUI 共用同一缓存路径。


### 2.8 【P1·易用性】无单实例、无互斥：多选右键拉起 N 个窗口、并发写同一目录

- **位置**：`App.xaml.cs` 全文（无 Mutex/命名管道，11-17 报告 P2-19 标注"按需求暂缓"，至今未做）。
- **后果**：资源管理器多选 N 个文件点右键 → N 个 GUI 进程各自弹密码框、各自批处理；同目录 `UniquePath` 竞态虽有重试，但用户体验是"弹了一堆窗口"。CLI 与 GUI 同时操作同一文件也无互斥（`FileShare.None` 只表现为 Locked 报错）。
- **修复**：命名 Mutex + 命名管道把后续实例的参数转发给首实例后退出（方案文档原本就描述了该设计）；管道消息复用现有 `AutoProcessPathsAsync`。这是右键工作流成立的前提，建议优先级上调。


### 2.10 【P2】目录名伪装的两个边界问题

- **位置**：`DirectoryObfuscator.cs:36-37`（`IsObfuscatedName` 只认前缀）与 `:76-78`（还原仅校验非法字符）。
- **问题**：① 用户自有目录若恰好以 `_hf_` 开头，会被"伪装"跳过、被"还原"误解码成乱码名甚至改名成功（Base32 解码+异或后只要字符合法就通过）；② 固定掩码异或任何人可逆（文档已声明定位，可接受），但**误还原他人目录**是数据事故。
- **修复**：还原前校验解码结果为合法 UTF-8 且不含控制字符；在混淆名中追加 4 字节校验尾（如 CRC32(原名) 的 Base32），还原时校验不匹配即拒绝；把"仅本工具产生的名字才可还原"变成可验证事实。

### 2.11 【P2】`scan`/`CollectFiles` 对大目录的 IO 与内存放大

- **位置**：`BatchProcessor.cs:50`（`Directory.EnumerateFiles` 后逐文件 `IsProtected` 开两次文件读魔数）；`StructureLocator.LocateMkv` 头尾各 8MB 缓冲。
- **问题**：十万文件级目录 scan 时每个文件 2 次 open/read；GUI `AddPaths` 在 UI 线程同步 `Inspect` 每个文件（`MainViewModel.cs:131-155`），大文件夹拖入会卡界面数秒到数十秒。
- **修复**：`Inspect` 移入后台任务 + 增量填充列表（`IProgress` 或 Channel）；魔数检测合并为一次 open 读头 8B+尾 8B；对 MKV 定位窗口按文件尺寸自适应（小文件不必 8MB）。

## 三、工程架构演进建议

### 3.1 引擎 API 去"全局可变配置"化（解决一类问题的根）

现状：`ObfuscateFile(path, config)` 依赖 `config.SessionPin` 与 `config.ProtectionMode` 两个**可变全局态**；GUI 用 `prevMode` try/finally 临时改写（`MainViewModel.cs:463-464,510`），CLI 直接改 config。这是模式串扰、并发批次、测试构造别扭的共同根源。

建议引入不可变请求对象：

```csharp
public sealed record ProtectionRequest(
    ProtectionMode Mode,
    byte[] MasterKey,          // 会话已解出的 MK
    byte[] ConfigSalt,
    string PinForWrapping,     // 仅用于生成新文件 emkBlob
    int HeadSize,
    bool RenameFiles,
    ExtensionRuleSet Rules);   // 从 config 快照而来
ProcessFileResult Protect(string path, ProtectionRequest req);
ProcessFileResult Restore(string path, Credential cred, ProtectionMode? expected);
```

config 只承担持久化与 UI 绑定；批处理器接收 request 快照。顺带解决：右键/工作台/CLI 三入口语义统一、测试无需构造整个 config、`rekey` 与"仅扫描"可复用同一入口。

### 3.2 凭据与密钥生命周期集中管理

现状：`_sessionPin/_sessionRecoveryCode/_sessionMasterKey`（VM）、`config.SessionPin`、CLI `TryGetLocalMasterKey` 三处各自缓存，一致性靠每个调用点人肉同步（`PromptSetPin`/`PromptChangePin`/`TryPromptCredential` 各自赋值一遍）；CLI 一条 `unhide` 命令甚至 `HideFilesConfig.Load()` 三次（`Program.cs:69,239,450`）。没有单一所有者，未来新增入口极易漏同步。

建议：Core 内 `KeySession` 类统一持有（MK、KEK 缓存、凭据来源、锁定/超时策略），实现 `IDisposable` 清零密钥字节；VM/CLI 只引用它。为后续"自动上锁（空闲 N 分钟）""Windows Hello 解锁"留出挂点。

### 3.3 容器格式治理：把"版本 2"变成可演进契约

- 现状：读取端 `ver != 2` 直接抛错（`V2Container.cs:127-128`、`V2Tail.cs:207-208`）；KDF 迭代数读取端写死常量（tag 5 是死字段，11-17 P2-14 已指出）；元数据 TLV 已具备"跳过未知 tag"的向前兼容。
- 建议：① 明确 v2 语义冻结文档（迭代数=600k 属于版本契约，改动即 bump version）；② 预留 v3 路线：**每文件 KDF 参数入头部**（Argon2id 的 m/t/p 或 PBKDF2 迭代数）、可选压缩标志、可选 Reed-Solomon 纠错标志（对照 Picocrypt [ref_web_e80f38bfdc52a5a937ecc132]）；③ 读取端遇到更高版本给出"请升级工具"而非笼统损坏提示；④ 增加**格式一致性测试向量**（固定密钥/盐/nonce 的golden文件入库），任何重构后跨版本互解有回归锚点——这是当前测试体系最缺的一环。

### 3.4 测试体系补强（60 项之外的空白）

当前 60 项全部针对 Core；**CLI 与 GUI 零自动化**（已核实 tests 无 Process/ViewModel 引用）。建议：
1. **CLI 端到端**：`dotnet run --project Cli` 子进程跑 setpin/hide/encrypt/unhide/scan/rekey 矩阵，断言退出码与 stdout（含 2.1 的右键参数矩阵：直接以 `--hide/--decrypt` 启动 App 不可行，但可把参数解析抽成可测函数）；
2. **GUI**： FlaUI/UIA3 冒烟（AutomationId 已埋好）：设置密码→拖入→加密→解密→恢复码路径；或至少把 `MainViewModel` 从 `Application.Current.Dispatcher` 解耦（注入 IDispatcher）后做 VM 级单测；
3. **故障注入**：结构加密写一半抛 IO 异常（流包装器）断言回滚后哈希一致；journal 恢复路径；配置损坏路径（2.3）；
4. **真实样本库**：≥256KB IDAT 的 PNG、尾部 Cues 的 MKV、带 EXIF 缩略图的 JPEG、moov 在尾部的 MP4 各一，入库或 CI 下载，断言锁定区清单；
5. **性能回归门槛**：400MB 样本结构加密 P95 < 1s 进 CI（本机基线已有），防止未来改动悄悄破坏核心卖点；
6. CI 目前不存在（无 .github/workflows）：建议 GitHub Actions `dotnet test` + `publish.ps1` 干跑 + 产物哈希留档。

### 3.5 发布与运行时生命周期

- **【重要】.NET 8 已于 2026-11-10 终止支持**（官方支持策略页确认，.NET 10 LTS 支持到 2028-11-14）[ref_web_c486d61cc4e16e386dbe5e5c][ref_web_ebd35ffd8eec2625e0f26328]。对一个**安全工具**而言，运行时不再有安全补丁是实质风险。建议升级 `net10.0-windows`（WPF-UI 4.x 与 CommunityToolkit.Mvvm 均兼容），顺带获得 crypto/JIT 性能改进；`publish.ps1` 增加 self-contained 单文件选项（当前 `--self-contained false` 要求目标机预装 Desktop Runtime，README 已写明但对"便携绿色"定位是摩擦点——Picocrypt 3MiB 免运行时的对照 [ref_web_e80f38bfdc52a5a937ecc132]）。
- 发布产物：`dist` 每次全删（11-17 P2-20②）改为按版本归档子目录；zip 内附 `SHA256SUMS.txt` 与版本说明；考虑 Authenticode 签名（无签名的加密工具极易被 SmartScreen/杀软误报，这是此类工具分发的第一障碍）；可选 winget manifest。
- `Directory.Build.props` 的 Debug 版本号含日期时间导致**不可复现构建**，建议 CI 用 `-p:ContinuousIntegrationBuild=true` 固定。

## 四、安全加固建议（按收益排序）

1. **删除 PinHash、以 unwrap 为唯一验证**（2.4）——消除离线快筛面，收益最大、改动最小。
2. **Argon2id 替换/并列 PBKDF2**：当前 600k PBKDF2 合规但 GPU 抗性弱于内存硬函数。Cryptomator 用 scrypt [ref_web_9bfecc721154947873b5f609]、Picocrypt 用 Argon2id(1GiB) [ref_web_9e6e9438fecf35b69ffe72eb]。建议在 v3 容器引入 Argon2id（可用 BCL 之外唯一值得引入的加密依赖，如 Konscious.Security.Cryptography，或 .NET 10 后评估内置方案），参数写入文件头；v2 文件保持可读。桌面场景 256MiB/t=3 是合理起点，解锁延时 ~0.5s 可接受。
3. **密钥材料内存卫生**：MK/KEK/fileKey 用后 `CryptographicOperations.ZeroMemory`；`SessionPin` 字符串无法清零是 .NET 限制，尽量缩短持有时间、改持 byte[]；对照 Picocrypt NG 2.16 "key material zeroed after use" 的发布说明 [ref_web_61aaa8105f39af3d974993bb]。
4. **自动上锁**：会话凭据空闲 N 分钟（默认 15）或系统锁屏时清除（`SystemEvents.SessionSwitch`），托盘/标题栏显示锁态；当前会话解锁后永久有效直到关窗。
5. **可选 keyfile（第二因子）**：Picocrypt 的 keyfile 思路 [ref_web_e80f38bfdc52a5a937ecc132]——MK 包裹密钥 = KDF(PIN) ⊕ HKDF(keyfile)，无 keyfile 即使 PIN 正确也解不开；对"密码可能被窥视"的威胁模型是质变。实现成本低（emkBlob 封装逻辑加一路输入），建议作为 v3 可选特性。
6. **恢复码治理**：展示分组+校验位（2.12f）、导出文件、保存确认（2.12e）；可选"恢复码重置密码"流程（Cryptomator recovery key 可重置 vault 密码 [ref_web_360f3207c67c39c7c9884529]）：输入恢复码 → 解出 MK → 允许设置新 PIN 重封装 config，把"忘记 PIN"从"只能逐文件用恢复码"升级为"一次性找回全部能力"。**这是当前恢复码体验与一线工具的最大差距。**
7. **结构加密的诚实标注**：UI 上给结构加密模式常驻一行说明"主体未加密，防打开不防提取；强保护请用整体加密"（架构文档已写，UI 未透出）；加密结果报告中标注每文件实际模式与锁定区数量，避免用户误以为两种模式等价。
8. **威胁模型文档化**：docs 增加一页"保护什么/不保护什么"（内存取证、交换文件、云同步明文缓存、缩略图缓存 thumbs.db 均不在保护范围），对照 Cryptomator 公开安全架构与 Cure53 审计的做法 [ref_web_cd21c10bcc0871967aa01ad4]——小工具做不到审计，但可以把边界写清楚，这本身就是可信度。

### 5.2 文件名混淆升级：从"哈希前缀"到"不可关联"

现状 `hf_<SHA256(主名+长度)前8位>` 有两个弱点：① 32bit 哈希同目录碰撞概率不可忽略（UniquePath 兜底了覆盖，但两名相撞会追加 (1)，暴露关联）；② 确定性映射意味着**同一文件在任何机器上同名**，攻击者可跨目录/跨设备关联同一文件，且可离线枚举常见文件名验证猜测。
建议：`hf_<Base32(HMAC-SHA256(MK, 随机8字节))截断>` + 随机盐入名，或直接用 AES-SIV(MK, 原名) 截断（Cryptomator 文件名方案 [ref_web_ea778d08f166ffa00f840130]）；原名已在加密元数据中，改名无需可逆。保留"关闭改名"开关不变。

### 5.3 "文件夹一键保护"组合动作

用户真实心智是"把这个文件夹藏起来"，而非分别操作文件与目录名。建议新增组合命令/按钮：`protect-folder` = 递归整体加密（或按规则结构加密）+ 目录名伪装 + 生成清单报告；`unprotect-folder` 逆向。内部复用现有原子操作，风险低、感知价值高。目录名伪装同时按 2.10 加校验尾。

### 5.4 Windows 11 右键菜单现代化

现状传统 `shell\` 注册表动词在 Win11 默认被折叠进"显示更多选项"，主菜单不可见——对以右键为核心入口的工具是**发现性硬伤**。微软文档明确：进入现代菜单需实现 `IExplorerCommand` 并注册 `windows.fileExplorerContextMenus`，未打包 Win32 应用需 sparse package [ref_web_4018a3190605e4cd4fdb947f][ref_web_7f29bb378668794aeed8d6ca]。
建议路线：① 短期在设置页说明文案中告知 Win11 用户需"显示更多选项"（管理预期）；② 中期实现 C# `IExplorerCommand` COM 服务器 + sparse package 注册（可用 CsWin32 生成互操作），保留传统注册表作为 Win10 回退；③ 菜单项按文件状态动态显示（已加密文件只显示"解密"，未加密只显示"加密"），`IExplorerCommand.GetState` 天然支持，比现在四个动词全列更清爽。

### 5.5 CLI 专业化

- 退出码语义文档化（0/1/2 已有，补"部分失败"与 dry-run 约定）；`--json` 机器可读输出（scan/处理报告），方便脚本与 GUI 复用；
- `--recursive/--no-recursive` 显式覆盖 config（当前只有 config 开关）；`--exclude` glob；
- `verify` 子命令：只校验容器完整性与凭据正确性、不落地明文（当前 scan 只看魔数，不解密验证）；
- 管道友好：`hidefiles encrypt - --pin-stdin` 支持 stdin/stdout 流式（整体加密天然流式，结构加密不支持则明确报错）；
- 补 `rekey`（2.5）、`recover`（四.6）、`repair`（2.7 journal 回滚）。

### 5.6 跨平台与生态（中长期，可选）

Core 已是 net8.0 纯 BCL（仅 ShellContextMenu 是 Windows-only），把 Core 拆出 `HideFiles.Core`（跨平台）+ `HideFiles.Shell.Windows` 后，CLI 可直接跑 Linux/macOS——容器自包含设计天然适合"Windows 加密、NAS/Linux 解密"的搬运场景，这是 Cryptomator 之外同类单文件工具少有的组合。GUI 跨平台不建议（WPF 绑定 Windows），保持 Windows 精品定位。

### 5.7 其他小而值的扩展

- **加密时可选压缩**（deflate，文档/文本类收益 50%+，媒体类自动跳过）；
- **处理报告与审计日志**（本地 JSONL：时间、模式、文件哈希前后、耗时；默认关，设置开启；不记录任何密钥材料）；
- **拖拽加密到目标文件夹**（当前只能原地；"加密并移动到…"是备份场景刚需）；
- **文件占用检测前置**：加密前提示被占用文件（当前处理到才报 Locked）；
- **多密码/多保险库**：当前单 MK 全局；支持"工作/个人"两个独立 MK profile 切换（config 多份密钥材料），满足"不同目录不同密码"的常见诉求，改动集中在 KeySession 与 config 结构。

## 六、UI/UX 易用性改进

### 6.1 信息架构

1. **合并双工作台为单列表+模式列**（可选激进方案）：两个 Tab 90% 结构重复（2.12g），用户还需理解"该去哪个 Tab 解密"。更贴近心智的模型是：一个文件列表，每行显示其容器模式徽章（结构/整体/未加密），操作按钮统一为"加密/解密"，加密时按行或全局选择模式；`expectedMode` 隔离改为按行自动匹配。若保留双 Tab，则至少做到 2.1/2.2 的路由正确性，并在 Tab 标题加计数徽章。
2. **设置页分区**：当前 5 张卡片平铺滚动；建议左侧二级导航（密码与恢复 / 加密选项 / 伪装规则 / 系统集成 / 数据与便携），对照 Cryptomator 设置分组；"保存设置"按钮离规则卡片太远，改为每卡片即时生效+全局"恢复默认"。
3. **首次运行引导**：三步向导（设密码→保存恢复码→拖入第一个文件），对照 Cryptomator 六步建库向导的"恢复密钥可选但强提示"设计 [ref_web_360f3207c67c39c7c9884529]；当前首次用户点加密才被动弹设置框，恢复码提示只在状态栏一闪而过（`MainViewModel.cs:391`），极易漏存——建议恢复码未确认保存前，主窗口顶部常驻琥珀色横幅。

### 6.2 反馈与状态

4. **每行进度与结果**：行内 spinner/进度（整体加密按字节进度，`BatchProgress` 已有计数，补当前文件字节进度即可）、成功✓/失败✗+原因 tooltip；批量结束弹可展开的结果面板（成功/失败分组、失败原因、重试失败项按钮），替代状态栏截断 3 条（2.12b）。
5. **取消与暂停**（2.12h）；处理中禁用"清空列表/移出"避免集合竞态（当前 `RemoveFile` 在处理中仍可点，`targetItems` 是快照但 UI 行消失会造成困惑）。
6. **空状态文案分模式**：结构加密页空状态写"支持 MP4/MKV/JPG/PNG 等媒体格式"（当前两页都写"支持任意格式"，与结构加密实际支持面不符，`MainWindow.xaml:93`）；整体加密页才写任意格式。这是文案级但直接影响首次成功率。
7. **深色模式与主题跟随**（2.12c）；状态徽章加图标/文字双通道（色盲可用）。
8. **快捷键**：Ctrl+O 选文件、Ctrl+Shift+O 选文件夹、Delete 移出选中、Ctrl+A 全选、Enter 对选中执行默认操作；密码框 Enter 已支持，保持。
9. **托盘与锁态**（可选）：最小化到托盘+空闲自动上锁（四.4）后，托盘图标区分锁/解锁态，双击唤起解锁框——与"会话缓存凭据"模型配套才安全。

### 6.3 信任与可理解性

10. **模式说明可视化**：加密按钮旁 info 图标弹出两模式对比卡（速度/保护强度/适用格式），把架构文档 §2 的取舍翻译成用户语言；结构加密结果行显示"已锁定 N 个结构区"。
11. **危险操作分级确认**：清除密码当前有二次确认（好）；"恢复默认设置"保留密钥（好）但无确认；建议对"清除密码"增加**要求输入恢复码后四位或勾选'我已离线保存恢复码'**的硬门槛（Cryptomator 对不可逆操作的警告范式 [ref_web_360f3207c67c39c7c9884529]）。
12. **关于页与截图更新**：`docs/screenshots/` 三张截图仍是 v1 单工作台+内嵌 PIN 输入框界面（已视觉核对），与当前双工作台+弹窗密码完全不符；README 无截图引用但 docs 报告引用了它们。建议重截并加入 README 首屏，关于页版本号改绑定（2.12i）。**过时截图对安全工具的可信度伤害大于功能缺失。**

# HideFiles v2 架构方案

> 本文档与当前代码严格一致。HideFiles 是一个 Windows 上的文件保护小工具，提供两种**彼此独立**的保护模式：结构锁（默认，极速）与整体加密（最强）。所有产物均为**单文件自包含容器**，可脱离工具与配置独立搬运。

## 1. 设计目标与取舍

| 目标 | 实现方式 |
|---|---|
| 防止他人直接读取/提取文件内容 | 用 PIN 派生密钥做真实 AES 加密，而非简单改扩展名 |
| 默认模式要极速、大文件秒级 | 结构锁只原地加密少量关键字节，不整体读写文件 |
| 不泄露原始文件类型 | 两种容器都使用统一魔数，与源格式无关 |
| 可独立搬运、改名 | 解密所需材料全部封装在文件自身（尾部或头部） |
| PIN 遗忘可恢复 | 生成一次性恢复码（主密钥的 Base32），可脱离 PIN 解密 |
| 小工具、不过度设计 | 零第三方加密/解析库，纯 .NET BCL；格式解析只定位关键结构 |

明确不做的：不追求"加密后仍可播放"，不兼容 v1 旧格式，不实现多用户/网络/插件体系。

## 2. 两种保护模式

### 2.1 结构锁（StructureLock，默认）

- **命令/按钮**：`hide`（混淆）、`unhide`（还原）；GUI「结构锁工作台」。
- **原理**：只加密"解码必需的少量结构"，媒体主体保持明文。对懂格式的人不是密码学级保护，但能挡住双击播放、通用工具和简单脚本，且极快。
- **原地操作**：不重写整个文件。加密"前 64KB 头部区 + 格式关键结构区"，然后在文件尾部追加一个约 118 字节固定 footer。
- **隐藏格式**：默认整段前 64KB 被 CTR 加密（可配置 4KB~1MB），覆盖 `ftyp` / EBML / JPEG SOI / PNG signature 以及常见的 moov、EBML 元数据区，hex 里看不到源格式签名，也不留下可直接解析的索引结构。
- **完整性**：每个被加密区存原始 CRC32（元数据 tag 8），还原时逐区校验，只读这几处，不读全文件。
- **失败安全**：锁定区原始字节全程留在内存（≤1MB，与文件大小无关），写入密文或 footer 任一环节失败都会写回原样并截断；footer 一次写入，长度与尾部魔数校验通过才视为提交。还原为两阶段（先全部解密并校验 CRC，全部通过才写回），失败后重试不会二次加密。
- **速度与文件总大小无关**：2GB mkv 实测混淆约 0.6s、还原约 0.3s（含进程启动与 PBKDF2）。10GB 同为秒级。

### 2.2 整体加密（FullEncrypt，可选）

- **命令/按钮**：`encrypt`（加密）、`decrypt`（解密）；GUI「整体加密工作台」。
- **原理**：整文件分块 AES-256-GCM（每块 64KB + 16 字节独立认证标签），全文件变乱码。没有 PIN/恢复码时裁头、砍尾、裸流均无法提取。
- **前置容器**：文件开头写入 120 字节头，随后是 GCM 加密的 TLV 元数据，随后是分块密文。需要整体重写文件。
- **完整性**：每块 GCM tag 提供逐块认证，外加原文件 SHA-256 整体校验。
- **速度**：硬件加速约 1.5–2.7 GB/s；50MB 解密约 18ms、200MB 约 120ms。

> 还原命令 `unhide` / `restore` / `decrypt` 语义等价：引擎自动识别容器类型（前置 or 尾部），按对应模式还原。因此"还原文件"和"解密文件"可以混用，只是 GUI 上分成两个独立按钮便于理解。

## 3. 容器格式

统一魔数均不含任何源文件签名，与源格式无关：

| 容器 | 魔数（十六进制） | 位置 |
|---|---|---|
| 整体加密（前置） | `89 48 46 0D 0A 1A 0A 9F` | 文件开头 |
| 结构锁（尾部） | `8A 48 46 0D 0A 1A 0A 9F` | 文件末尾 |

### 3.1 整体加密容器（前置）

```
[Header 120B] [MetaCipher 变长] [分块密文]
Header: magic(8) ver(1) mode(1) flags(1) reserved(1) configSalt(16)
        fileSalt(16) fileNonce(12) emkBlob(60) metaLen(4)
每块密文: [明文长度 4B][AES-256-GCM 密文 N B][tag 16B]
```

### 3.2 结构锁容器（尾部）

```
[原文件字节：头部区(默认前 64KB) + 关键结构区已被原地 CTR 加密] [Footer]
Footer（从文件末尾往前）:
  [metaCipher 变长][metaLen(4)][configSalt(16)][fileSalt(16)]
  [fileNonce(12)][emkBlob(60)][mode(1)][ver(1)][magic(8)]  固定尾部 118B
```

## 4. 元数据（TLV，整体 GCM 加密）

两种模式共用 `V2Metadata`，以 `tag + 变长长度 + 值` 编码，读取端跳过未知 tag（向后兼容）：

| Tag | 内容 |
|---|---|
| 1 | 原始文件名 |
| 2 | 原始扩展名 |
| 3 | 原始长度（int64） |
| 4 | 锁定区域清单（offset, length, kind） |
| 5 | KDF 迭代次数 |
| 6 | 原文件 SHA-256（整体加密模式使用） |
| 7 | 保护模式 |
| 8 | 各锁定区原始 CRC32 列表（结构锁模式使用） |

## 5. 密钥体系

```
PIN（低熵） + configSalt --PBKDF2-HMAC-SHA256(600000)--> KEK
KEK + 随机主密钥 MK --AES-256-GCM--> emkBlob(60B) = nonce(12)+cipher(32)+tag(16)
MK + fileSalt --HKDF(HMAC-SHA256)--> fileKey
fileKey --> 元数据 GCM 加解密 / 结构锁 CTR / 整体加密分块 GCM
恢复码 = Base32(MK)，可脱离 PIN 直接还原
```

- emkBlob 写入**每个文件**（前置头或尾部 footer），文件自包含，拷到任意机器有 PIN 即可还原。
- config.json 只保存 PIN 的加盐哈希（用于快速校验）、configSalt、用 PIN 加密后的 MK、恢复码哈希；**不保存明文 PIN 或 MK**。
- **修改 PIN 只重封装 MK**：`ChangePin(newPin, currentPin)` 先用当前 PIN 解出 MK、再用新 KEK 重新封装，MK 与恢复码都不变，此前保护的文件仍可用新 PIN 还原；绝不在改 PIN 时生成新 MK。首次设置 PIN 才生成 MK 并返回恢复码。
- **解密时的密钥解析顺序**（`V2Crypto.ResolveMasterKey`）：恢复码 → 文件自带 emkBlob + 用户 PIN → 本机 config 中当前 PIN 对应的 MK。第三条用于"改过 PIN 后文件内 emkBlob 仍是旧 PIN 封装"的场景；钥匙是否正确最终由元数据 GCM 认证标签判定，误用只会得到明确的"PIN 或恢复码不匹配"。
- config.json 兼作"本机已改 PIN"的解密兜底：CLI 与 GUI 都会缓存/复用这份 MK，批量还原只跑一次 PBKDF2。
- 结构锁 CTR：counter block = `nonce(12) || 4 字节块序号`，每个锁定区用 `BlockNonce(fileNonce, region.Offset)` 派生独立 nonce，避免密钥流复用。
- 整体加密 GCM nonce = `BlockNonce(fileNonce, 块序号)`，元数据使用保留序号 `ulong.MaxValue`。

## 6. 格式关键结构定位（`StructureLocator`）

纯 BCL 解析，只读必要的头部/盒结构，不引入第三方库。找不到结构时结构锁**直接报错**（文件不动），提示改用整体加密，绝不静默降级成"假保护"。

| 格式 | 定位并加密的结构 |
|---|---|
| MP4 / M4V / MOV | 递归 box 树，锁定 `stco` / `co64` / `stsc` / `stsz` / `stss` / `avcC` / `hvcC` / `esds` 载荷 |
| MKV / WebM | EBML VINT 解析，锁定 `CodecPrivate`（SPS/PPS）、`Cues`、`SeekHead` |
| JPG / JPEG | SOI 之后到 SOS 之前的参数段（DQT/DHT/SOF/APPn） |
| PNG | `IHDR` 数据块 + 首个 `IDAT` 数据块头部 |

## 7. 模块与职责

```
src/HideFiles.Core/
├── CoreConstants.cs      v2 常量、魔数、模式枚举 ProtectionMode
├── V2Crypto.cs           PBKDF2 / HKDF / AES-GCM / emkBlob / Base32 恢复码
├── V2Metadata.cs         TLV 元数据编解码
├── V2Container.cs        整体加密：前置容器读写、分块 GCM 主体
├── V2Tail.cs             结构锁：原地 CTR 加密 + 尾部 footer 读写 + CRC 校验
├── StructureLocator.cs   四种格式的关键结构定位
├── FileObfuscator.cs     统一入口：Inspect / ObfuscateFile / RestoreFile（自动识别容器）
├── HideFilesConfig.cs    配置持久化、PIN/恢复码、保护模式开关
├── BatchProcessor.cs     批量处理与进度
├── ShellContextMenu.cs   四动作级联右键菜单（注册表，仅当前用户）
└── DirectoryObfuscator.cs 目录名可逆混淆（独立操作、幂等）
src/HideFiles.Cli/        CLI：hide/unhide/encrypt/decrypt/setpin/scan/menu
src/HideFiles.App/        WPF GUI：结构锁工作台 / 整体加密工作台 / 设置 / 关于
```

`FileObfuscator` 保留稳定的公共接口（`Inspect` / `ObfuscateFile` / `RestoreFile`），`RestoreFile` 通过容器魔数自动分派到尾部（结构锁）或前置（整体加密）读取路径。

## 8. 命令与 GUI 对应关系

| 语义 | CLI | GUI 工作台按钮 | 右键菜单项 | 实际模式 |
|---|---|---|---|---|
| 混淆 | `hide --pin` | 结构锁 · 混淆文件 | 混淆文件 (结构锁·极速) | StructureLock |
| 还原 | `unhide --pin/--recovery` | 结构锁 · 还原文件 | 还原文件 (结构锁) | 自动识别（通常尾部） |
| 加密 | `encrypt --pin` | 整体加密 · 加密文件 | 加密文件 (整体·最强) | FullEncrypt |
| 解密 | `decrypt --pin/--recovery` | 整体加密 · 解密文件 | 解密文件 (整体) | 自动识别（通常前置） |

GUI 启动参数与右键菜单一致：`--hide` / `--unhide` / `--encrypt` / `--decrypt` / `--open`，后接路径。还原时弹出 `PinVerifyDialog`，可输入 PIN 或切换到"使用恢复码"；凭据仅驻留内存会话，不落盘。

## 9. 目录与文件命名

- 混淆/加密后默认生成 `hf_<8位哈希><伪装扩展名>`，扩展名按规则组映射（视频→`.dat`、图片→`.tmp`、音频→`.bin`、压缩包→`.bak`）；关闭文件名混淆时保留原名与原扩展名（整体加密模式下即为原地替换原文件，不产生第二个文件）。
- 还原时从元数据读取原始文件名，逐字节恢复（SHA-256/CRC 校验通过后才提交）；原始文件名只取文件名部分，目录成分会被剥离，避免元数据被篡改后越目录写入。
- **目标文件已存在时绝不覆盖**：自动改为 `原名 (1).扩展名` 递增（`UniquePath`，移动使用 `overwrite: false` 并对竞态重试）；仅当原名与容器名相同时才原地替换。
- 整体加密写入采用"临时文件 + 同卷 rename"，中途失败不会留下半个目标文件；结构锁为原地加密（失败回滚见 §2.1）。

### 9.1 目录名混淆（独立操作）

与文件混淆互不影响，只处理目录名本身：

- 入口：CLI `dir-hide` / `dir-unhide`；GUI「规则与系统设置」→「目录名混淆」。
- 算法：UTF-8 字节按位置掩码异或后 Base32 编码，前缀 `_hf_`。确定性、可逆、无需密钥、无需索引文件。
- 幂等：已带 `_hf_` 前缀的名称直接跳过，重复执行不会二次混淆。
- 范围：只改给定目录**内部**的子目录，自最深一层往上改名，不改动给定目录自身（调用方路径始终有效）。
- 冲突：目标名已存在时自动加 `(1)`；混淆后超过 200 字符直接报错（截断会破坏可逆性）。
- 安全定位：只降低可读性，本工具自身即可还原；不是加密，也不做完整性校验。

## 10. 已知边界

- 结构锁的媒体主体是明文，挡不住专门分析格式的攻击者；需要强保护请用整体加密。
- 两种模式加密后都不能直接播放/预览，必须先还原。
- PIN 与恢复码二者丢失后无法还原（强加密的必然结果）。
- 不兼容早期 v1（头部 XOR）格式；旧文件请先用旧版本还原。

## 一、总体评价

代码整体结构清晰，文档与实现大体对应，v2 的密钥体系设计正确：PBKDF2(60 万次) → KEK → 包裹 MK，MK + fileSalt → HMAC 派生 fileKey，每个文件独立 fileSalt/fileNonce，AesGcm 使用 12 字节 nonce + 16 字节 tag，结构锁用 AES-CTR 保持长度不变。实测真实样本（400MB MP4 / 7MB JPG / 3.6MB PNG）结构锁往返 SHA-256 逐字节一致，400MB MP4 混淆 375ms、还原 132ms，性能指标与文档吻合。

但存在**若干会造成数据丢失或使保护强度显著低于文档承诺的实质缺陷**，其中三项在我这里已 100% 复现（还原静默覆盖同名文件、改 PIN 导致历史文件失效、PNG 结构锁退化），另有一项设计级风险（结构锁原地改写无回滚）。**建议在对外分发前修复 P0 项**。

## 二、P0：数据安全类缺陷

### P0-1 还原时静默覆盖同名文件，造成不可逆数据丢失（已复现）

**位置**：`src/HideFiles.Core/FileObfuscator.cs:221-223`、`:253-254`；混淆侧 `:155-156`、`:181`

```csharp
// 结构锁还原
string targetPath = Path.Combine(dir, read.Metadata.OriginalFileName);
if (!string.Equals(filePath, targetPath, StringComparison.OrdinalIgnoreCase))
    File.Move(filePath, targetPath, overwrite: true);   // ← overwrite: true
```

**实测**（探针 2）：把 `doc.mp4` 整体加密 → 用户在该目录又新建了一个同名 `doc.mp4`（内容 `NEW-IMPORTANT-FILE-CREATED-LATER`）→ 执行还原 → 新文件被旧内容静默覆盖，无任何提示、无备份、无回收站。

混淆侧同样使用 `File.Move(..., overwrite: true)`，且新名由 `SHA256(baseName + len)` 取前 **8 位十六进制（32 bit）**生成，同目录下文件名+长度相同的重复文件会命中同一目标名，直接互相覆盖。

**影响**：用户在整理、多次搬运、重名场景下会丢文件，且事后不可恢复（不是移动到回收站）。

**建议**：目标已存在时不覆盖，改为 `原名 (1).扩展名` 递增；或先备份到 `.bak` 再替换；至少要在覆盖前要求显式确认。混淆侧同理，并且应扩大到 `overwrite: false` + 名称冲突重试。

### P0-2 结构锁原地改写原文件，缺少回滚与备份（文档承诺与实现不符）

**位置**：`src/HideFiles.Core/V2Tail.cs:40-114`（`ProtectInPlace`）、`src/HideFiles.Core/FileObfuscator.cs:144-157`

`ProtectInPlace` 直接在原文件上 `FileAccess.ReadWrite` 逐区 CTR 加密，最后才追加 footer。任一步骤异常（断电、磁盘满、杀软拦截、进程被杀）都会留下"关键结构已被加密、但没有 footer"的文件：既不是明文，也不再是任何有效容器，**无法用任何 PIN/恢复码还原**。

`docs/架构方案.md` §9 写的是"写入采用临时文件 + 成功后再替换，中途失败不破坏原文件"——该承诺只对整体加密近似成立，对默认模式（结构锁）不成立；`README.md` 又把结构锁作为默认推荐，风险面因此放大。

**建议**：**只回滚被改写的锁定区，绝不做整文件暂存**。

> 勘误（2026-11-17 21:15）：本报告初版曾建议"先复制整个文件到 `.hfstaging`、加密后原子替换"。该方案等价于整体重写，2GB 文件要多写 2GB、10GB 多写 10GB，正好推翻结构锁"耗时与文件大小无关"的核心设计（见 `CHANGES-20261117.md` 20:28 条），不可采用。正确做法如下。

`ProtectInPlace` 现有实现本来就是"逐区读进 `byte[] buf` → 加密 → 写回"，原始字节天然在内存里，因此回滚成本与文件大小无关：

1. 先把全部锁定区原始字节读进内存（MP4 单区上限 1MB、MKV 256KB、JPEG 64KB、PNG 4KB；实测 400MB MP4 共 7 区合计 723KB，**≤ 约 1MB**）。加密必须作用在副本上，不能像现在这样就地异或 `buf`，否则原始字节同时丢失。
2. 逐区写回密文并 `Flush(true)`；再追加 footer 并 `Flush(true)`。
3. 重读 footer（`ReadFooter`，只读几百字节）做**提交点判定**：能解出元数据才算成功。
4. 提交成功后才返回。

失败处理分两级，都不触碰文件主体：

- **进程内异常**（磁盘满、IO 错误、编码缺陷，覆盖绝大多数实际失败）：`catch` 中用内存副本把各锁定区写回原样、`SetLength(origLen)` 截掉半截 footer，再抛原异常。额外 IO 仅几百 KB。
- **硬崩溃**（断电、进程被强杀）：此时进程内回滚来不及，才需要落盘备份 `filePath + ".hfbak"`（magic + 区域清单 + 原始字节 + CRC，同样只有几百 KB）。恢复入口不交给用户自己猜：`Inspect`/启动自检发现同目录存在 `.hfbak` 且对应文件已不是有效容器时，提示"检测到未完成的操作，可回滚"。该层属可选加固，只解决硬崩溃。

即使只实现第一级（内存回滚），也已是零性能代价的净收益。

### P0-3 修改/重置 PIN 会重建主密钥，历史文件立即失效（已复现）

**位置**：`src/HideFiles.Core/HideFilesConfig.cs:79-102`（`SetPinV2` 每次 `RandomNumberGenerator.GetBytes(32)` 新 MK）；调用点 `MainViewModel.SavePin`（`:184-194`）、`MainViewModel.SaveConfig`（`:314-331`）、`CLI Program.ExecuteSetPin`（`:123-141`）、`MainViewModel.ResetConfig`（`:333-340`）、`ClearPin`（`:196-205`）

**实测**（探针 5）：用 `old-pin` 加密文件 → 用户"修改 PIN"为 `new-pin` → 用 `new-pin` 还原**失败**（`authentication tag did not match`），只能用**旧恢复码**还原；新旧恢复码不同，说明 MK 已被重建。

这是 GUI 文案"设置/修改 PIN"直接诱导用户操作的路径，却是隐形的密钥销毁动作：用户改一次 PIN，所有已保护文件当场只能用一张可能早已不知道丢哪去的旧恢复码来救。`ResetConfig`（"重置为默认配置"）与 `ClearPin` 同样会清掉 `WrappedMasterKey`，效果更彻底。

**建议**：
1. "修改 PIN"必须是**重封装同一 MK**（`UnwrapMasterKeyWithPin(旧PIN)` → `WrapMasterKey(新KEK)`），而不是生成新 MK；
2. 只有在"首次设置 PIN"时才生成 MK；
3. 重置/清除 PIN 前做二次确认，并强制展示当前恢复码或要求确认"已知悉历史文件将无法再用 PIN 还原"；
4. CLI `setpin` 增加 `--rekey`（重建，需显式指定）与默认"不改 MK"两种语义。

### P0-4 GUI 没有任何恢复码入口，PIN 丢失即等于 GUI 无法还原

**位置**：`src/HideFiles.App/ViewModels/MainViewModel.cs:169-181`、`:287`；`src/HideFiles.App/Views/PinVerifyDialog.xaml`（仅 PasswordBox）

`RestoreFile(item.FilePath, _sessionPin)` 只传 PIN，`PinVerifyDialog` 只有密码框，没有"用恢复码还原"的入口。当 `Config.HasPin == false`（用户点过"清除 PIN"）时 `EnsurePinVerified()` 返回 true，`_sessionPin` 仍为 null，每个文件都以"还原需要 PIN 码或恢复码"失败，而这条错误还被丢弃不显示（见 P2-1）——界面上表现为"点了没反应"。

## 三、P1：功能正确性与保护强度

### P1-1 PNG 结构锁在真实文件上退化到 64 字节头部（已用真实样本复现）

**位置**：`src/HideFiles.Core/StructureLocator.cs:213-226`

```csharp
int clen = BinaryPrimitives.ReadInt32BigEndian(scan.AsSpan(p, 4));
if (clen < 0 || p + 12 + clen > scan.Length) break;   // ← 用整个 chunk 长度判断窗口
...
if (type == "IDAT") { regions.Add(new LockRegion(p + 8, Math.Min(clen, 4096), "IDAT")); }
```

扫描窗口只有 256KB，但判断用的是 IDAT 的**完整长度**。只要首个 IDAT ≥ 约 256KB（大图、截图几乎都如此），循环直接 `break`，IDAT 永远不会被锁定。

**实测**（探针 7 / 探针 10）：

| 样本 | 定位到的锁定区 |
|---|---|
| 合成 PNG，IDAT=64KB | `IHDR@16+13, IDAT@41+4096` ✔ |
| 合成 PNG，IDAT=300KB | `IHDR@16+13` ✘ |
| 合成 PNG，IDAT=4MB | `IHDR@16+13` ✘ |
| **真实 3.6MB `file-03.png`** | **1 个区，合计 13 字节**，落盘合并后仅 64 字节 |

对真实大 PNG，结构锁实际只加密了 64 字节文件头，与文档"锁定 IHDR 数据块 + 首个 IDAT 数据块头部"不符，保护强度远低于宣称（虽然仍能挡住"双击打开"，但 IDAT 数据完全明文，比文档描述的弱得多）。

**建议**：判断改为只校验所需的头部前缀是否在窗口内（`p + 8 + Math.Min(clen, 4096) <= scan.Length`），或按 chunk 长度合法跳过而不中断扫描。

### P1-2 头部区合并时长度被回缩，导致部分关键结构漏加密（已复现）

**位置**：`src/HideFiles.Core/V2Tail.cs:51-61`

```csharp
foreach (var r in meta.LockRegions.OrderBy(r => r.Offset))
{
    if (r.Offset < headLen)
    {
        int end = (int)Math.Max(headLen, r.Offset + r.Length);
        regions[0].Length = Math.Min(end, (int)origLen);   // ← 直接赋值，未与既有长度取 max
        continue;
    }
    ...
}
```

按 offset 升序合并，但 offset 升序不等于"结束位置"升序。若两个区都落在前 64 字节内，且先出现的是长区、后出现的是短区，第二次赋值会把第一次扩大的长度改回较小值。

**实测**（探针 3）：构造 `LockRegions = [(16,+200), (33,+10)]`，本应覆盖 `0..216`，落盘后锁定区变成 `HEADER-SIG@0+64`——**152 字节本应加密的结构保持明文**（因为加密也按合并后的清单执行，所以是可逆的，不会损坏数据，但保护被静默削弱）。

**建议**：`regions[0].Length = Math.Max(regions[0].Length, end)`，并顺手去掉多余的 `(int)origLen` 强制转换（见 P2-11）。

### P1-3 结构锁没有任何文件级完整性校验

**位置**：`src/HideFiles.Core/V2Tail.cs:88-89`、`:197-202`；`FileObfuscator.cs:216-230`

CRC 只覆盖被加密的几个区，主体明文区完全没有校验，也不校验 `BodyLength == meta.OriginalLength`。

**实测**（探针 9）：把尾容器主体中部（第 5000 字节，非锁定区）翻转 1 位，还原**成功**且不报错，产出内容错误的文件。

文档已声明"媒体主体是明文"是设计取舍，但"还原成功"意味着用户会信任这个结果。至少要加一条零成本的校验：`BodyLength == meta.OriginalLength`（可捕获截断/拼接/重复追加 footer 等情形）。

**建议**：补长度一致性校验；提供可选"高完整性模式"（还原时对全文件做 SHA-256，读写成本已包含在同一遍 IO 内）。

### P1-4 整体加密的分块长度前缀无范围校验，可触发溢出或超额内存分配

**位置**：`src/HideFiles.Core/FileObfuscator.cs:357-378`

```csharp

byte[] cipher = new byte[n];              // n 可为负数或 2GB
byte[] tag = new byte[16];

```

**实测**（探针 4）：篡改首块长度前缀为 `-1`（该字段在 GCM 认证范围之外，可直接修改），还原报错为 `Arithmetic operation resulted in an overflow.`——用户看到的是看不懂的底层异常，而非"容器已损坏"。若改为 `0x7FFFFFF0`，则会在认证前申请约 2GB 内存。

### P1-5 `RestoreInPlace` 非幂等：失败后重试会把已解密区重新加密

**位置**：`src/HideFiles.Core/V2Tail.cs:181-210`

循环内"读 → 解密 → 校验 CRC → 写回"。若第 i 个区 CRC 失败抛异常，前 i-1 个区**已经以明文写回文件**，footer 也未被截断。用户看到失败后通常会再点一次"还原"：此时前 i-1 个区被 CTR 再次异或 → 又变回密文，而 footer 仍在，最终文件处于"部分密文被当成明文再加密"的混合状态，彻底不可逆。

**建议**：两阶段执行——先全部读取并校验 CRC，全部通过后再统一写回；或写到临时文件后原子替换。

### P1-8 整体加密双倍写盘，吞吐被腰斩

```csharp
string targetPath = Path.Combine(dir, newName);
if (string.Equals(filePath, targetPath, StringComparison.OrdinalIgnoreCase))
    targetPath = Path.Combine(dir, $"hf_{Guid.NewGuid():N}{fakeExt}");  // ← 关掉开关也会改名
```

`ObfuscateFileName=false` 时 `targetPath == filePath`，兜底逻辑把名字改成 `hf_<32 位 guid>.png`。

**实测**（探针 1）：设置 `ObfuscateFileName=false` 后混淆 `photo.png`，结果文件名变为 `hf_c49f7e31ddc247d3913c90c4ed36ed90.png`。

**建议**：结构锁模式下若 `targetPath == filePath` 直接跳过 `File.Move`（原地加密本来就不需要改名）；整体加密模式改为"写临时文件 → 原子替换回原路径"，就无需这条兜底命名，`File.Delete` 也可省掉。

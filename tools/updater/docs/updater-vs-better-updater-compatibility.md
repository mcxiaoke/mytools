# updater 与 better-updater 兼容性与替代可行性深度对比报告

> 生成时间：2026-09-15  
> 比对对象：
> - 现有版本：`c:\Home\Projects\mytools\tools\updater`（包含 `rust/` 极简版与 `go/` 历史版）
> - 目标版本：`C:\Home\Projects\mytools\tools\better-updater`（工业级崩溃自愈完整基线）

---

## 1. 核心结论摘要

### 1.1 是不是超集？
**在系统可靠性与功能维度上是大幅跃升的“超集”，但在命令行接口（CLI）与运行时契约上不是 100% 的“严格超集（Strict Superset）”。**

- **可靠性跃升**：从“纯内存回滚栈”升级为“磁盘持久化 Journal + 备份对账 + L1/L2/L3 三层自愈（含看门狗守护）”，彻底解决了任意时刻被杀软强杀、用户强制关机导致半新半旧不可恢复的痛点。
- **能力增强**：支持影子工作进程（安装目录内直接自更新）、版本与降级防范、保留上一版本及离线一键回退（`--rollback-previous`）、Ed25519 签名验证、Restart Manager 占用诊断。
- **接口不兼容**：由于参数单位差异、缺失 GUI 相关参数、退出码语义调整、提权后默认降权等原因，**现有主程序若直接无感平替（Drop-in Replacement），在特定传参或调用方式下会直接报错或行为不及预期**。

### 1.2 能否完全替代？
**结论：可以完全替代！两处参数不兼容（`--gui`/`--gui-title` 与 `--max-uncompressed`）现已全部改造对齐完毕。平替时仅需留意以下 2 项集成实践：**
1. 确认调用端主程序以 **Detached 进程启动更新器后立即退出自身**，不阻塞等待 updater 退出码（避免受影子 Worker 异步交棒影响）；
2. 确认管理员权限应用若使用 `--elevate`，是否需配合 `--keep-elevation`（防止被默认降权回普通 Medium 权限）。

## 3. 核心差异与不兼容陷阱深度解析

### 3.1 原生 GUI 进度对话框已完成移植对齐（`--gui` / `--gui-title`）
- **落地状态**：
  已将原生 Win32 进度窗口及双语本地化模块（`gui.rs` 与 `strings.rs`）移植入 `better-updater`（标记为 `// Tier: 2`，直接依赖数保持 7，符合架构分层守卫）：
  - **分阶段动效**：预检及等待目标进程退出期间启用系统原生跑马灯（Marquee），文件原子替换阶段自动平滑无缝切换为真实百分比进度（Smooth 0~100%）并展示实时文件路径；
  - **双语原生自适应**：调用 Win32 `GetUserDefaultUILanguage()` 自动识别系统语言（`zh-CN` 中文，其余全英文），支持 `--gui-title` 自定义标题；
  - **独立 UI 线程与防假死**：专属 UI 线程与 Win32 消息循环，非阻塞 IPC 进度投递，杀软扫描或大包写入时窗口永不出现“(未响应)”；
  - **完全兼容**：现有调用方传入 `--gui` 或 `--gui-title` 均已原生支持，行为与体验完全一致。

---

### 3.2 参数单位明确：`--max-uncompressed` 统一为整数 MiB
- **决议**：
  为避免魔数模糊推断（如依据大于或小于 100,000 隐式猜测单位），双方 CLI 契约已严格统一为 **整数 MiB**：
  - 参数定义：`--max-uncompressed <MiB>`（默认值统一为 `4096`，即 4 GB）；
  - 传参规范：若调用方需要限制总解压大小，直接传入整型 MiB 数值（例如 `--max-uncompressed 2048` 代表 2GB，`--max-uncompressed 4096` 代表 4GB）；
  - 绝大多数桌面客户端缺省不传该参数，直接享用 4GB 默认容量。

---

### 3.3 差异 3：影子工作进程（Shadow Worker）导致退出码与进程模型变化
- **现状**：
  - `updater`：主进程全程同步运行。如果检测到自身在 target 内，只做“无条件跳过自身文件”，主进程依然会执行所有文件的覆盖，拉起新程序后正常退出（退出码 0 代表全部更新成功）。
  - `better-updater`：如果检测到自身在 target 内（为了达成“updater 自身随更新包更新”的能力），会在启动早期将自身复制到 `%LOCALAPPDATA%\...\runtime\` 并派生一个 **影子 Worker 进程（Shadow Worker）**。此时：
    **主实例将自身任务交接给 Worker 后，立即返回退出码 0 退出！**
- **影响**：
  - 优点：完美解决了安装目录内的 `updater.exe` 被锁定而无法被新版本覆盖更新的问题。
  - 潜在破坏点：如果主程序的调用代码存在**反模式**——例如主程序以同步等待方式执行 `updater.exe` 并等待退出码：
    1. 主程序会发现 `updater.exe` 在几百毫秒内就返回了 `0`；
    2. 主程序若误以为更新已完成，尝试立刻重新初始化或占用目标目录文件，此时后台的影子 Worker 才刚刚开始执行文件替换；
    3. 结果引发文件共享冲突（Sharing Violation）。
- **对策**：
  所有调用端必须遵守主程序集成黄金法则：**主程序派生更新器必须以 Detached（分离进程）模式拉起，且主程序在派生后必须立即 `exit(0)` 退出自己**，由更新器在最终阶段通过 `--launch` 负责拉起新版本。

---

### 3.4 差异 4：提权后（`--elevate`）的权限降权行为（De-elevation）
- **现状**：
  - `updater`：使用 `ShellExecuteExW("runas")` 提权拉起自身；更新成功后通过 `CreateProcessW` 拉起 `--launch`。此时拉起的新版本主程序将**无条件继承管理员权限（High IL）**。
  - `better-updater`：提权更新成功后，执行拉起时：
    ```rust
    let want_deelevate = args.elevated_worker && !args.keep_elevation;
    win32::de_elevate::launch(&launch, &args.args_raw, &args.target, want_deelevate);
    ```
    它会通过寻找当前桌面会话的 `explorer.exe` 进程令牌，**主动将拉起的新程序降权回标准普通用户权限（Medium IL）**！
- **影响**：
  - 针对绝大多数桌面应用（如 Flutter/Tauri），降权是巨大的修复（因为管理员权限的窗口无法接收普通 Explorer 的文件拖拽，且网络盘映射会丢失）。
  - **但若主程序本身就是一个必须要求管理员权限的系统维护工具**：直接替换后，用户会发现更新完拉起的新版软件变成了普通权限，导致其功能异常！此时必须在参数中追加 `--keep-elevation`。

---

### 3.5 差异 5：等待目标 PID 超时时的退出码语义
- **现状**：
  - `updater`：等待目标 PID 释放超时时，走 `abort()` 逻辑，返回 **退出码 1**（与中途写入失败同码，并尝试兜底拉起旧版本）。
  - `better-updater`：等待 PID 退出是放置在“全部无损预检通过后、磁盘写入之前”。超时则认为“磁盘零改动中止（Aborted）”，返回 **退出码 2**。
- **影响**：
  监控脚本若根据退出码区分预检错误（2）与运行时错误（1），会发现超时分类发生变化。

---

### 3.6 差异 6：版本控制与降级防护（Version Guard）
- **现状**：
  - `updater`：不解析任何版本号，包内有什么文件就覆盖什么文件。
  - `better-updater`：引入了 `updater.manifest`。若更新包内包含清单，更新器会把版本号写入 `<target>/.updater/state`。
    如果下一次下发更新包的版本号**低于**已安装版本号（如线上发生重大 Bug，紧急推送旧版本回滚包）：
    `better-updater` 会判定为版本回退攻击，**直接拒绝更新并返回退出码 2**！
- **影响**：
  若存在下发降级包的运维操作，必须要求在参数中显式加上 `--allow-downgrade`，否则无法执行降级。

---

### 3.7 差异 7：Ed25519 签名校验机制（Fail-closed 策略）
- **现状**：
  - `updater`：不支持数字签名，仅支持弱校验 `--sha256`。
  - `better-updater`：内置 Ed25519 验签模块。
- **影响**：
  - 目前代码库中的 `RELEASE_PUBLIC_KEYS` 为空数组（`unsigned-build`），行为表现为记录一条警告后跳过验签，当前与 `updater` 兼容。
  - **但需警惕**：一旦编译时在代码内写入了发布公钥，`better-updater` 将进入 `fail-closed` 模式——更新包旁边必须存在 `.sig` 签名文件，否则直接拒绝更新（退出码 2），且 Release 构建下即便传入 `--allow-unsigned` 也会被强制忽略。

---

### 3.8 差异 8：目录常驻布局与自愈契约
- **现状**：
  - `updater`：运行时产生临时目录 `.updater_tmp/` 和 `.updater_bak/`，更新成功后**全部删除**，target 目录无任何常驻残留。
  - `better-updater`：更新机制基于事务 Journal，更新后在 target 根目录**常驻保留隐藏系统目录 `<target>/.updater/`**，包含：
    - `state`：当前版本状态；
    - `lock`：独占并发锁；
    - `previous/`：保留的上一版本文件（供 `--rollback-previous` 使用，默认保留 7 天）。
- **影响**：
  1. **调用方清理逻辑冲突**：如果宿主主程序在启动时有自净逻辑（例如扫描安装目录下所有未识别的文件并自动删除），**必须把 `.updater/` 加入白名单**，否则会损坏事务现场并抹除版本回退能力。
  2. **自愈契约（推荐落地）**：`better-updater` 具备冷启动自愈能力。最理想的调用方集成是在主程序启动时检测如果存在 `<target>/.updater/journal`，先同步调用 `updater.exe --recover --target <dir>` 修复现场。

## 5. 当前仅存的 5 项行为差异与调用端核对清单

经过本次改造，所有**参数名称、参数单位、GUI 报错等接口级不兼容已全部消除**。两者的差异现在只剩下以下 5 项**运行期底层机制与安全行为的差异**：

| # | 差异项 | `updater` (当前) | `better-updater` (目标) | 调用端配合建议 |
| :-: | :--- | :--- | :--- | :--- |
| **1** | **提权后的权限** | `--elevate` 后新主程序继承管理员权限（High IL） | `--elevate` 后**默认通过 Explorer 降权为普通权限（Medium IL）** | 普通桌面应用无需操作（享受降权利好）；若程序必须以管理员身份运行，调用时追加 `--keep-elevation` |
| **2** | **安装目录常驻** | 临时目录全部清理，无常驻残留 | 常驻隐藏系统目录 `<target>/.updater/`（存放 Journal、状态与上一版备份） | 若宿主应用启动时有扫描安装目录清理未知文件的自净逻辑，必须将 `.updater/` 加入白名单，严禁删除 |
| **3** | **自更新生命周期** | 在 target 内启动时，跳过自身（不更新自身） | 在 target 内启动时，**影子 Worker 接棒，主实例瞬间返回 0 退出** | 确保主程序遵循 Detached 启动后立即 `exit(0)` 的规范，严禁同步阻塞等待 updater 退出码 |
| **4** | **版本与降级** | 不检查版本号，任意包直接覆盖 | 若包内含 `updater.manifest`，**默认拦截降级包**（报退出码 2） | 正常发版升级无需处理；若线上需紧急推送旧版本回滚包，调用时追加 `--allow-downgrade`；不打包清单则跳过检查 |
| **5** | **等待 PID 超时** | 退出码为 `1` | 退出码为 `2`（视为预检未触碰磁盘的中止） | 均会自动尝试兜底拉起旧版本，外部监控脚本若区分预检错误与运行时错误需知悉 |

## 6. `better-updater` 独有高级特性汇总（纯正向收益）

1. **强杀掉电可自愈**：磁盘持久化 Journal + 备份对账 + L1/L2/L3 三层自愈，任意写入瞬间遭外部强杀绝不残留半新半旧不可用状态；
2. **一键离线版本回退**：本地保留上一版本备份（默认保留 7 天），出现严重问题时无需网络下载，调用 `updater.exe --rollback-previous --target <dir>` 即可秒级还原；
3. **Restart Manager 占用诊断**：遇到文件被杀软或同步盘占用时，日志自动记录具体占用的进程名称与 PID，排障一目了然；
4. **数字签名验证体系**：原生集成 Ed25519 验签模块（当前公钥留空，默认跳过验签；未来需要时可随时启用编译期固化密钥）。

# 机械师 G7 2.4G 鼠标 WebHID 协议逆向分析

> 分析对象: https://www.machenike.com/G7/#/ 的网页驱动
> 样本: `mouse/temp/js/index-B1Q7iOow.js`(3.6MB 主包) + `mouse/temp/js/driveGather-33aEb_qg.js`(1.3MB 通信库)
> 日期: 2026-10-14（已实测验证：两个工具均读到真实电量 93%）

## 1. 样本解混淆

两个包都是 webpack + javascript-obfuscator(字符串数组 + 控制流平坦化)。
解混淆脚本: `mouse/temp/deob.js`(Node, 零依赖)。

```
node deob.js js/driveGather-33aEb_qg.js deob/driveGather.deob.js   # 5627 字符串, 替换 14682 处
node deob.js js/index-B1Q7iOow.js    deob/index.deob.js            # 14454 字符串, 替换 40259 处
```

原理: 提取 `function _0xXXXX(){var arr=[...]}`(字符串数组) + 数组轮转 IIFE + decoder,
在 vm 里还原数组后, 把所有 `decoder(0xNNN)` 调用替换为真实字符串字面量。
解混淆产物在 `mouse/temp/deob/`。

## 2. 设备结构（USBTreeView + WebHID + 实测三重确认）

厂商 **Telink**，USB 复合设备，VID `0x320F` / PID `0x226F`，2 个 HID 接口：

| 层 | 接口 A | 接口 B |
|---|---|---|
| USB 接口 | MI_00（鼠标，EP1 IN 8B） | MI_01（键盘，EP2 IN 64B + EP5 OUT 64B） |
| Chrome HIDDevice | collections `0C:01 \| FF00:00 \| FF01:00` | collections `0C:01 \| FF1C:92` |
| 报告大小 | report 4/5 = **8 字节**（7 负载 + ID） | report 4 = **64 字节**（63 负载 + ID） |
| 用途 | 标准鼠标/系统控制 | **网页驱动的厂商协议接口** |

驱动过滤器: `{usagePage: 0xFF1C, usage: 0x92, vendorId: 0x320F, productId: 0x226F, connectionType: 2}`。
**用户最初用 WebHID Explorer 看的是接口 A（7 字节报告），驱动走的是接口 B**——这就是报告大小对不上的原因。

Windows 侧每个顶层 collection 还是独立设备路径（`mi_XX&colYY`），共 9 条，实测 caps：

```
mi_01&col02: usagePage=0xff1c usage=0x0092 IN=64B OUT=64B   ← 驱动接口
mi_00&col05: usagePage=0xff00 usage=0x0000 IN=8B OUT=8B FEAT=8B
mi_00&col06: usagePage=0xff01 usage=0x0000 FEAT=8B
其余: 000C:0001(Consumer, IN=3B) / 0001:0080(IN=2B) / 启动鼠标键盘(\kbd)
```

## 3. 通信协议（实测验证）

核心函数 `communicateWithDevice(cmd, retry, maxRetry, param4)`：

```
发送: sendReport(0x04, 63 字节载荷)
载荷: [00 00 CMD SUB 00*27 NESTED]     (CMD 在 data[2], NESTED=2 在 data[31], 2.4G 模式)
接收: inputreport, reportId=0x04, 63 字节 data
响应: [00 00 CMD SUB 00 00 00 DATA ... NESTED]   (回显命令, DATA 在 data[7])
超时: 2000ms, 最多重试 3 次
```

命令表：

| CMD  | SUB  | 尾部参数 | 作用 | 响应数据位 |
|------|------|---------|------|-----------|
| 0x01 | 0x18 | NESTED | 会话开始 | - |
| 0x02 | 0x18 | NESTED | 会话结束 | - |
| 0xAA | 0x00 | (8 字节载荷) | 2.4G 配对检查 | data[7]/data[8]，ff=该槽位未配对 |
| 0x30 | 0x10 | param4(槽位) | 读 cid（设备标识） | data[9]（十进制） |
| 0x19 | 0x18 | NESTED | 电量查询前置 | data[7]（驱动丢弃） |
| **0x1A** | **0x06** | NESTED | **读电量** | **data[7] = 电量%(0-100)** |
| 0x03/05/07/08/0A/1B | - | - | 配置/按键矩阵/灯效读写 | data[7] 起 |

## 4. 电量读取（实测输出）

```
→ sendReport(0x04) 00 00 19 18 00*27 02
← inputreport id=0x04 data=00 00 19 18 00 00 00 00 ...
→ sendReport(0x04) 00 00 1A 06 00*27 02
← inputreport id=0x04 data=00 00 1A 06 00 00 00 5D ...   ← data[7]=0x5D=93%
```

即：**先 0x19 再 0x1A，取响应 data[7] 即电量百分比**。
注意：鼠标休眠时响应全 0，需移动/点击鼠标唤醒后再读。

## 5. 网页端电量显示逻辑

`mode-battery-power` 结构（`Machenike Driver.html` 实证）：

```
keyboard-profiles > h4 "设备模式及电量"
  └ mode-battery-power
      ├ [img /G7/mode/2.4G.svg] + "2.4G模式"        (connectionType==2)
      └ [img /G7/mode/electricity{1,3}.svg] + "93%"
```

图标逻辑：`connectionType==1 → electricity2.svg`（有线）；
`connectionType==2 → 电量>10% ? electricity1.svg : electricity3.svg`（正常/低电量）。

### Python 版踩过的坑（x64 Windows HID，ctypes）

1. `SetupDiGetDeviceInterfaceDetailW` 的 `cbSize` 必须是 `sizeof(结构)`=**8**（写死 6 被拒，枚举返回 0 接口）。
2. `HIDP_CAPS` 必须定义全 **38 个 USHORT（76 字节）**，少字段会导致 `HidP_GetCaps` 堆越界 → 随机段错误。
3. `FILE_FLAG_OVERLAPPED` 句柄的 `WriteFile` 必须传真实 `OVERLAPPED`（传 NULL → err=87）。
4. `ctypes.wintypes` 没有 `OVERLAPPED`，要自己定义。
5. Windows HID 缓冲区**首字节必须是 report ID**（04），载荷布局 `[00 00 CMD SUB 00*27 NESTED]`，CMD 在 wire[3] 而非 wire[2]。

## 2026-10-07 11:00:35 — 代码评审修复：危险级体量触发死代码、交互下 -y 失效、中途失败退出码、保留名处理

- **背景**：对全部实现做了一轮代码评审，确认 4 个问题（其中 2 个用探针/实验实证），本次一并修复。
- **修复 1（P0）危险级的"体量"触发是死代码**：`scanLimits` 把扫描早退上限设为
  `danger_file_threshold` 本身，而扫描计数逐条 +1，截断时计数**恰好等于**阈值；
  `Decide` 用"严格大于"比较，单目标永远无法升为危险级（实测 6000 文件的目录只走到
  确认级）。早退上限改为**阈值 + 1**，并新增 `TestEndToEndDangerLevelBulkBoundary`
  边界用例（3/9/10/11 个文件 → 无需确认/确认级/确认级/危险级）。
- **修复 2（P0）交互终端下 -y/-f 不跳过确认级**：`SkipConfirm`/`YesIAmSure` 此前只在
  `Ask` 的非交互分支生效，TTY 下即使带 `-y` 也会打印摘要并阻塞等待输入（EOF 按取消
  处理）。预授权判断提前到环境判定之前，交互与非交互语义一致；新增
  `TestAskPreApprovalAppliesInBothEnvironments` 与
  `TestEndToEndInteractiveYesSkipsConfirmLevel`。
- **修复 3（P1）多卷批次中途失败的退出码会撒谎**：前面组已移动成功后，后续组
  `EnsureRoot`/`Begin` 失败直接返回退出码 1（语义"未发生任何移动"），且已完成组的
  操作号/清单路径不再打印。新增 `setupFailed` 统一出口：`opLines` 非空时按部分失败
  （退出码 2）结算并打印已有成果，否则维持退出码 1。
- **修复 4（P1，处理方式从简）Windows 保留设备名改为预检拒绝**：实测（探针 +
  实验）确认两条死路——Go 1.26 的 `filepath.Abs` 会把 `C:\work\nul` 整个改写成
  `\\.\nul`（目录前缀丢失），Win32 对普通路径又把保留名解析成设备；自建 `\\?\`
  verbatim 转换收益覆盖不了成本（参考 coreutils `rm` 与 safe-rm 也都不做特殊处理）。

  （新增 `literal_windows.go`，按"基础名 + 任意扩展名"识别 con/prn/aux/nul/com1-9/

  与 Windows 自带 `del` 行为一致。新增 `TestAbsCleanRejectsReservedDeviceNamesOnlyOnWindows`
  （Linux 上 `nul` 是合法文件名，绝不拒绝）与 `TestReservedDeviceNameTargetIsRejected`。

## 2026-10-07 09:53:01 — 危险级触发条件收窄：只有"目标自身是仓库根"才危险

- **问题**：`ui.DetectGit` 从目标逐级向上找 `.git`，命中即升危险级。这是**常开**信号——
  开发者几乎所有文件都在某个仓库里，于是 `saferm -y` 在任何真实项目里都失效，
  结局必然是养成无脑加 `--yes-i-am-sure` 的习惯，危险级形同虚设。
  与 §14 D10 否掉"目标在 cwd 之外"是同一条理由：**常开的信号不能用来分级**。
  写 E2E 脚本时就撞上了这一点——夹具放在项目 `temp/` 下会全部变成危险级，只能挪到仓库外。
- **改动**：
  - `ui.GitInfo` 新增 `IsRepoRoot`（目标**自身**直接含 `.git`/`.hg`/`.svn`），并保留
    `InRepo`/`RepoRoot` 供展示。两者成本差一个数量级：`IsRepoRoot` 只需 3 次 `stat`（抽成
    `hasVCSMarker` 复用），`InRepo` 才是逐级向上找。
  - `ui.Decide` 的 Git 危险信号改为 `IsRepoRoot`（原来用 `InRepo`）。**危险级因此收窄为
    "体量"与"目标自身是仓库根"两类**。
  - "目标自身是仓库根"仍算危险信号，是因为护栏第 8 条本来就拒绝它（除非被 `--allow-dangerous`
    绕过或 `protect_vcs_root = false`），这里正好是第二道防线。
- **明确不做**（§14 D12）：**不递归扫描目标子树里的 `.git`**。代价是"删除一个内部含嵌套仓库的
  目录"不会被特别提示；换来的是判定成本 O(1)、常见路径上不比 `rm` 慢。已记入设计文档 §5.3 已知局限。
  另外把这条的判断依据写清了：本工具**只移动不删除**，被一并搬走的仓库完整躺在回收目录里、
  清单在旁边、随时能搬回，代价只是恢复成本。
- 测试：
  - `ui.Decide` 三条新语义：仓库根→危险级；仅在仓库内的文件→不升级；仓库内的目录按体量走确认级。
  - `cmd` 两个危险级用例改用"仓库根 + `protect_vcs_root=false`"（正好覆盖"护栏被绕过后的第二道防线"）。
  - 新增回归用例 `TestEndToEndInRepoTargetNoLongerNeedsDangerFlag`：仓库内普通目标 `-y` 必须够用。
  - `config_test` 的 `git_detect` 用例重写为"关掉它 → 不再升危险级、不再显示仓库"。
  - 两个 E2E 脚本第 7 节重写为"仓库内普通目标只需 -y；仓库根默认被护栏拒绝、放开护栏后危险级接手"，
    用例数 55 → 59，两份脚本仍逐条对称。
- 文档：设计 §6.1 第 5 步重写（含"为什么不再是危险级"的引用块）、§14 新增 D11/D12、§5.3 已知局限、

  §7 Agent 建议第 4 条、§8 新增第 4 项；CLI `--help` 文案。
- **新增 `tools/saferm/.gitattributes`**：把 `*.sh` 钉成 LF、`*.ps1` 保持 CRLF。

  所有文本文件在工作区都会变成 CRLF**，那会让 `tests/*.sh` 的 shebang 变成

## 2026-10-07 09:25:58 — 实施兼容性报告的三项改进，并修掉两个静默失败缺陷

- 新增 `cmd/saferm/rmcompat.go`，把"从 rm 迁移"的接口集中到一处：
  - `addRMCompatFlags`：注册 `-r`/`-R` 与 **`--preserve-root`**。后者用自定义 flag 值
    （`ignoreFlagValue` + `NoOptDefVal`）实现，因此 `--preserve-root`、`=true`、`=all`
    **三种写法都能收**——依据是 GNU 9.4 的文档就是 `--preserve-root[=all]`；若用 `BoolVar`，
    `=all` 会报出莫名其妙的 "invalid argument"。其中 `=all`（拒绝删除与父目录不同设备的参数）
    本来就是 saferm 的行为：挂载点会被当作卷根拒绝，且回收根必须与目标同卷，所以接受它零安全成本。
  - `rmOnlyFlags` + `rmCompatHint`：对 rm 有而 saferm 故意没有的参数
    （`-d`/`--dir`/`-I`/`--interactive`/`--one-file-system`/`--no-preserve-root`）
    给出**等价写法**。`--` 之后的内容是路径，不再套提示。
  - `reportFlagError`：先打 pflag 的原始错误，再补等价写法。
- **修 bug（静默失败）**：参数解析失败时，pflag 在 `ContinueOnError` 模式下**不会**自己打印错误
  （`failf` 只在其它模式下打印），而原代码只打了一句"用法：…"，用户**完全不知道是哪个参数错了**。
  现在先打出原始错误。同一个成因在 `saferm where` 上更严重：它遇到未知参数是**退出 1 且零输出**，
  现在会给出原因 + 用法。
- **修 bug（子命令不一致）**：`where` 有自己独立的 flagset，没有共用 rm 兼容面，
  于是 `saferm where --preserve-root` 被当成未知参数。现在 `-r`/`-R`/`--preserve-root`
  在所有子命令上行为一致。
- `--no-preserve-root` **仍然拒绝**：它要求关闭卷根保护，与本工具的存在意义冲突。
  拒绝时也会说明原因（而不是只丢一句用法）。
- 设计文档 §8.2：参数表补 `--preserve-root` 行；补充原则"未知/不支持的开关绝不静默忽略，
  必须说清是哪个参数、并对已知 rm 参数给出等价写法"，并指向兼容性报告。
  README：参数表补 `--preserve-root`；新增**「从 rm 迁移」**小节（三件必知事项 + before/after
  对照表 + 退出码提醒）；测试小节列入 `tests/compat-rm-vs-saferm.sh`。
- 新增 `cmd/saferm/rmcompat_test.go`（8 个测试函数）：`--preserve-root` 三种写法都被接受、
  `--no-preserve-root` 被拒绝且说明原因、5 个不支持参数必须"点出参数 + 给出等价写法"、
  真正陌生的开关不套 rm 提示、`--` 之后不套提示、`where` 未知参数必须报错、
  `where` 接受 `--preserve-root`、`-rf`/`-ry`/`-r` 组合仍照旧可用。
- **重新在 WSL 实测**（沿用 `tests/compat-rm-vs-saferm.sh`）：31 个场景中
  **退出码一致 24→25、终态一致 25→26**（场景 30 `--preserve-root` 由不一致变为一致）。
  残留 9 处差异 = 4 处**有意**的行为差异（`-f` 配空变量、整批原子性、引号通配符、`-i` 非交互）
  + 4 个不接受的 rm 参数（`-d`/`-I`/`--one-file-system`/`--no-preserve-root`）。

## 2026-10-07 09:04:43 — rm 兼容性实测（WSL）与兼容性报告

- 新增 `tests/compat-rm-vs-saferm.sh`：对**同一份场景**分别跑 GNU rm 与 saferm，
  记录退出码、退出后沙箱的实际内容、搬进回收区的条目数。31 个场景，
  沙箱放在 `/tmp` 下的独立目录（不在 Git 仓库内，避免触发"仓库内 → 危险级"而失真），
  `saferm` 一律加 `--trash-root` 隔离回收区，stdin 接 `/dev/null`（脚本/CI 的真实处境）。
- **"退出码一致"与"终态一致"分开统计**，因为两者不是一回事：`rm` 的 `1` 可能是
  "删掉了一部分还报错"，而 saferm 的 `1` 是"整批预检没过，一个都没动"。只看退出码会漏掉场景 18。
- 测试环境：WSL2 Ubuntu，内核 6.18.40.1-microsoft-standard-WSL2，非 root 用户，
  GNU coreutils 9.4，`/tmp` 为 ext4。saferm 用交叉编译出的 `build/saferm-linux-amd64`
  （**WSL 里没装 Go，也用不着**——直接跑交叉编译产物，这也顺带验证了 Linux 二进制可用）。
- 结果：**31 个场景中 24 个退出码一致、25 个终态一致**。7 个退出码不同：
  `-f` + 空串（#5）、引号包住的通配符（#16）、`-i` 非终端（#20）、`-I`（#27）、
  `--one-file-system`（#29）、`--preserve-root`（#30）、`--no-preserve-root`（#31）。
- 最需要注意的三条差异：
  1. **`-f` 配空变量：`rm -f ""` 静默成功（退出 0），saferm 退出 1。** 这是本次事故的成因，
     属**有意为之**的特性，但它会让现存脚本里"未校验变量 + `-f`"的写法直接失败。
  2. **整批原子性**：`saferm a.txt c-missing.txt` 一个都不动（退出 1），
     而 `rm` 会把存在的那个真删掉（也退出 1）。saferm 失败后重试是安全的，rm 不是。
  3. **未识别的 rm 参数直接报用法错误**，不静默忽略（`-d`/`-I`/`--one-file-system`/
     `--preserve-root`/`--no-preserve-root`）。这比静默忽略安全（尤其 `--no-preserve-root`），
     但要求迁移时逐个改参数。
- 新增交付物：
  - `docs/COMPAT-rm-vs-saferm-20261007.md`：兼容性报告（退出码语义对照、参数支持对照、
    31 场景表、六个行为差异及实测输出、脚本迁移清单、agent 使用建议、改进建议、未覆盖项）。
  - `docs/COMPAT-rm-vs-saferm-20261007-raw.md` + `-detail.txt`：原始测量数据（汇总表 + 逐例 stdout/stderr 原文）。
- 报告里提出三条**尚未实施**的改进建议：① 接受 `--preserve-root` 作为 no-op
  （saferm 的卷根保护恒为开启，接受它零安全成本，能救掉一批脚本，约两行代码）；
  ② 未知开关的报错里给出等价写法提示；③ README 增加"从 rm 迁移"小节。
- 本轮修掉两个 harness 自身的坑（不是产品缺陷）：`--trash-root` 必须放在用例参数**之前**，
  否则遇到 `--` 结束符的场景会被当成 operand；回收区条目数只应统计操作目录**内部**，
  否则会把 `.saferm-trash-root` 标记与 `.op.json` 清单一起算进去（曾把 1 个文件报成 3 个）。
- 已知未覆盖：TTY 交互路径（确认输入、危险级手敲名字）在非 TTY 下无法复现，
  由 Go 测试覆盖，但**退出码 3 在真实终端下的可达性本轮未实测**；
  退出码 2（部分失败）需要"预检通过但移动中途失败"，本轮没构造；
  Windows 上没有 GNU rm 可比；macOS/BSD 的 rm 语义未测。

## 2026-10-07 08:58:51 — 第 8 步：源码不变量扫描接入质量门

- 新增 `internal/invariants`（`doc.go` + `invariants_test.go`），把设计文档 §10.1 的 C8
  （"v1 的代码里不存在任何永久删除调用"）从口碑变成**可机械验证**的结论。两条断言：
  - A. 全库（**含测试文件**）不出现任何删除类调用；
  - B. **非测试源码**里对 `os` 的"写入类"调用必须落在 `os.Rename` / `os.Mkdir` /
    `os.MkdirAll` / `os.WriteFile` 之内——将来有人加 `os.Chmod`、`os.Truncate`、
    `os.OpenFile` 会被拦下，逼着人明确"这算不算允许"。
- **用 `go/ast` 解析而不是正则扫文本**，理由是正则会被这两种情况骗过：

  `windows.DeleteFile` / `syscall.Unlink` 必须抓到；注释里提到、字符串里出现、
  自己类型的同名 `Remove` 方法必须**不**误报；测试文件里造夹具的 `os.Symlink` 不报。

## 2026-10-06 21:27:53 — 第 2 步：卷识别、回收根解析与 `where`

- platform 新增：`ListVolumes`（Windows 用 `GetLogicalDrives` 并过滤掉打不开的空读卡器/断开的网络驱动器；Linux 读 `/proc/self/mounts` 并过滤伪文件系统）、`IsWritableDir`（无副作用的可写性探测）。
